# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Development rules

- **After every new feature**, update both `README.md` and `CLAUDE.md` to reflect the new capability — add it to the relevant section in the Features list of each file.

- **After adding support for a new airline**, update the supported airlines table in `README.md`, the airline rules count and list in both `README.md` and `CLAUDE.md`, and increment `PARSER_VERSION` in `backend/parsers/builtin_rules.py` (a version mismatch makes the next sync a full rescan).

- **Email fixtures carry real mail, so scrub them everywhere before committing** — not only the HTML body, which is the only place the early passes touched. Personal data also hides in: PDF attachments (passenger names and two dates of birth survived there until they were redacted with PyMuPDF), RFC2047-encoded headers (a surname sat inside the SAS e-ticket's `Subject`, invisible to any raw-text search), attachment filenames (e-ticket numbers), booking references, frequent-flyer numbers, and ESP tokens in URLs — the Lufthansa `?enc=`, Austrian e-paper and BA `?code=` links are manage-my-booking deep links, not just trackers. `backend/tests/test_fixture_privacy.py` is the tripwire for the common shapes; it is not a proof, so read a new fixture before adding it. After rewriting a fixture, prove the change is inert by diffing extraction before/after rather than trusting the suite: several assertions loop over the extracted flights and pass vacuously on an empty result.

- **After every implementation**, always run all three checks before considering the work done:
  1. `uv run ruff check backend/` — fix any lint errors (use `--fix` for auto-fixable ones)
  2. `uv run ty check backend/` — fix all type errors
  3. `cd frontend && npm run lint` — fix any ESLint errors

- **Always write tests** for every new feature or bug fix without being asked:
  - **Backend**: for a layered feature package (`backend/<feature>/` with routes/service/repository — e.g. `notifications`, `packing`, `expenses`, `boarding_passes`, `shares`), place its tests in `backend/tests/<feature>/`, mirroring the package (`test_repository.py`-style files per layer plus the black-box `test_api_*.py`). For everything else, place tests directly in `backend/tests/` following existing patterns. Both use: class per module, `asyncio.run()` for async, `test_db` fixture, mock with `unittest.mock`. Keep coverage above 70%.
  - **Frontend**: add unit tests as `*.test.ts` files alongside the source (e.g. `utils.test.ts`, `ComponentName.test.ts`) using Vitest + `@testing-library/svelte`. Run with `npm test` inside `frontend/`. Both are already configured.
  - **E2E**: for every new feature, add a Playwright test in `frontend/tests/` as a `*.spec.ts` file. E2E tests require the server running at `http://localhost:8000`. For bug fixes, E2E is optional but preferred if the fix touches a user-facing flow.

```bash
# Setup
uv sync

# Run
uv run uvicorn backend.main:app --reload

# Lint
uv run ruff check backend/

# Type check
uv run ty check backend/

# Dead code detection (manual, review output — expect false positives from FastAPI handlers)
uv run vulture backend/ --exclude backend/tests/

# Parser coverage over the local email corpus (data/ is gitignored; see the corpus note below).
# Run before and after any parser change and diff the output — a mail that matches a rule
```

## Architecture

**Partiu** is a self-hosted flight tracker PWA. Flight data flows from email → IMAP fetch → HTML/PDF parse → SQLite → REST API → Svelte frontend.

### Backend (`backend/`)
- **`main.py`** — FastAPI app entry point; mounts frontend static files, initializes DB, starts scheduler and SMTP server
- **The SPA catch-all resolves through `_resolve_static_file`, never `base / full_path`.** That join was an *unauthenticated arbitrary file read* — `serve_spa` is deliberately unauthenticated and `FirstRunMiddleware` only gates `/api/` paths, so anyone who could reach the port could read any file the process could. Two vectors reached it and closing one is not a fix: an **absolute** path parameter makes pathlib discard the base entirely (`Path("dist") / "/etc/passwd"` is `/etc/passwd`), reachable from a browser bar as `GET //etc/passwd` because the doubled slash leaves `/etc/passwd` in the parameter; and **percent-encoded** traversal (`GET /..%2f..%2f.env`) is decoded into the parameter *after* the server's own path normalisation, so `..` survives to the handler. Both were confirmed against the running app — the second returned `.env`, and `SECRET_KEY` is what decrypts the stored IMAP and Immich credentials, so the read chained to full mailbox compromise. The helper resolves both sides and tests containment, which also covers symlinks out of the tree, and a rejected path falls through to the SPA shell rather than a 403 so the route never reports which files exist. Note `/assets` is a Starlette `StaticFiles` mount and was never vulnerable — only the hand-rolled catch-all was. `test_static_path_traversal.py` pins every vector and is written against the helper rather than over HTTP, because an HTTP client normalises some of these before they are sent and the assertions would pass without testing anything.
- **`database.py`** — Raw sqlite3 (no ORM), WAL mode, connection helpers (`db_conn`/`db_write`), Alembic migration bootstrapping, and `init_database()`'s startup sequencing (credential-encryption migrations + aircraft-type normalization/seeding). Domain-table seed data and queries live in their owning package's repository (`airports/repository.py`, `integrations/aircraft/repository.py`), not here.
- **`scheduler.py`** — APScheduler runs email sync every 10 min and aircraft sync daily
- **`sync/pipeline.py`** — Main pipeline: fetch emails → parse → extract flights → group into trips (via `sync/grouping.py`); `use_llm` flag enables LLM fallback for incremental sync (disabled for full rescan). `sync/service.py` (the `/api/sync/*` routes' use-case layer) calls into it rather than owning the pipeline itself.
- **`parsers/engine.py`** — Rule matching + `merge_flights`, plus the multilingual `parse_flight_date`. `match_rule_to_email` also reads *forwarded* headers out of the body, and the labels are localised to the **forwarder's** UI language, not the sender's (Gmail in pt-BR writes `De:`, not `From:`) — matching English only meant forwarded itineraries reached no rule. Deliberately holds no extraction logic of its own any more: the generic PDF pattern that used to be merged into every rule's result was removed with the line scanners
- **`parsers/shared.py`** — Helper library every airline extractor builds on (`scan_flights`, `resolve_iata`, `make_flight_dict`, date/time helpers). Two things here are load-bearing for correctness across all airlines: (1) `make_flight_dict` is the single choke point where a leg can be refused, and it enforces `validate_flight_number` — SAS prints `SK1829 | Airbus A320neo` and `A3` (Aegean) is in its codeshare prefix list, so aircraft types were being stored as flights; (2) `scan_flights`' two-line lookbehind prefers IATA codes found at or after the flight-number line, because on a multi-leg itinerary the lookbehind otherwise reaches into the *previous* leg's arrival airport and collapses the leg to `BCN → BCN`
- **`parsers/gds_eticket.py`** — Airline-independent parser for GDS ticket receipts (ITR / ITR-EMD). Handles three renderings of the same document: the **table layout** (HTML `<tr>` per leg — a cell's meaning comes from its column), the **compact layout** (`AF 871 / 12NOV Cape Town - Paris CDG 07:55 19:15`, found in the PDF attachment when the HTML part is only a cover note), and the **fixed-column layout** — the classic Amadeus ITR as monospace text in a `<pre>` (`STOCKHOLM ARLAN TP 783  T  10NOV 1905`, the arrival on the next line as `ARRIVAL TIME: 2235`). That one truncates place names to the column width, so name resolution is *expected* to fail on some of them and the baggage block's bare pairs (`ARNLIS`) settle the route. Two things about that corroboration are load-bearing: pairs standing **alone on a line** are tried before the loose six-capitals scan, because the loose scan reads `LISBON` as (LIS, BON) — and BON is Bonaire, a real airport — which made the real `LISARN` ambiguous and dropped the leg; and the same receipt is usually in the body **twice** (fixed-width text plus a whitespace-collapsed copy of the HTML), so columnar legs are deduplicated on number, date and time. It reads the PDF itself rather than relying on the caller having folded PDF text into `body`. Compact-layout dates carry no year, so `_resolve_receipt_date` resolves them *forward* from the issue date — a receipt is always issued before travel, which is why that inference is safe here and not in `validation.py`. **Extraction order in `sync/pipeline.py` is by trustworthiness: (1) the airline's own rule, (2) this GDS parser — *merged* into the rule's result via `engine.merge_flights`, not used only as a fallback, (3) LLM.** Merging (rather than falling back) matters because an airline rule can silently drop legs on a multi-carrier itinerary — an ARN→AMS→LHR→JNB ticket came through the SAS rule as the final leg alone. There is no generic-line-scanner tier between (2) and (3) any more, and `test_gds_eticket_parser.py::TestExtractionOrder` fails if one is reintroduced — see the pipeline comment where it used to sit
- **`parsers/schema_org.py`** — Reads the published schema.org reservation markup that booking platforms embed next to the pretty HTML. Categorically different from every other parser here: there is nothing to guess at, so it either finds a typed `LodgingReservation` or returns `[]`. That is what earns it the right to run on senders `_NON_FLIGHT_DOMAINS` blocks — the blocklist exists because *heuristic* parsing of accommodation mail produced junk, and a structural reader cannot. Deliberately **not gated on sender**: Airbnb was the only platform with markup in the 372-email corpus (Booking.com's two mails carry none), but keying on today's senders would mean a code change for every platform that ever adopts the standard. Reads **both spellings of the check-in pair**: Google's Gmail markup reference says `checkinDate`/`checkoutDate` (what Airbnb writes) while schema.org's own vocabulary says `checkinTime`/`checkoutTime` (what KDE Itinerary reads and Hotels.com annotates with) — handling only one is a silent miss, the worst failure mode here since it produces no error and no stay. Handles both renderings — JSON-LD (`<script type="application/ld+json">`, Airbnb's form, sometimes entity-escaped so a failed `json.loads` is retried through `html.unescape`) and microdata (`itemscope`/`itemprop`, the form every flight-markup airline uses). The microdata parser tracks nesting by **element depth**, not by matching end tags: marketing HTML wraps markup in plain `<div>`s and a "pop when the tag matches" scheme closes the item on the first inner `</div>`, collapsing a reservation to its first two fields. The one judgement call is `_wall_clock`: **a UTC offset in this markup is discarded and only the wall clock kept.** Three of six real Airbnb records carried an offset and all three were wrong — a flat `+01:00` on properties in France, Italy and Poland, all on CEST — because it was UK time at the stay date, i.e. the *recipient's* site locale (`airbnb.co.uk`), not the property's zone. The wall clock was right every time, and `StayService` re-localises it from the property's own coordinates, so honouring the sender's offset takes a right answer and breaks it
- **A boarding pass enriches a flight; it never creates one.** `lufthansa._extract_f3` reads the mobile boarding pass, which prints flight number, route, date and *departure* time and carries no arrival time at all. It used to stand the departure in for the arrival, producing a zero-length leg that `validation.py` discarded on every sync — nothing was ever stored, and the only trace was a log line reading like a parse failure rather than a format missing a field. It now returns `[]`, and `extract_boarding_pass_details` patches the seat, gate, terminal, cabin, reference and passenger onto the leg the traveller already has. This is the rule `_process_bcbp_email` has always followed ("we don't have enough info to create a complete flight from BCBP alone"), and a mobile pass carries strictly less than a barcode does. Measured across the 372-email corpus, all three emails in this format were for legs already stored from their booking confirmations. An airline opts in by exporting `extract_boarding_pass_details`; `builtin_rules._resolve_boarding_pass_extractor` binds it the same dynamic way `extract` is bound, so adding one needs no change there. LATAM is the second airline to opt in (`latam.extract_boarding_pass_details`): its "Aqui está o cartão de embarque" mail prints flight number, a `dd/mm/yy` departure, the seat under an `Assento` label and the booking code, and ten of the thirty LATAM mails in the corpus are this template or its predecessors — all of which yielded nothing before. Only the 2024+ template carries a seat; the older "Cartão de embarque atualizado" prints flight and date alone and still enriches nothing, correctly. The pipeline fills **only empty fields** — the booking confirmation is the authority on the route, and a pass reprinted after a gate change must not overwrite a seat edited by hand
- **Do not add an "arrival must differ from departure" guard to `make_flight_dict`.** It looks like the obvious place to catch the placeholder above and it is wrong: at that point the two are **naive local times at each end**, so AY813 leaving Helsinki 14:00 and reaching Stockholm 14:00 is a real one-hour flight across a one-hour offset. Adding the guard silently dropped both Finnair legs from the corpus. Only `apply_airport_timezones` makes the instants comparable, so ordering is `validation.py`'s call; a parser with no arrival time must return nothing rather than invent one. `test_lufthansa_boarding_pass.py::test_equal_local_times_are_still_a_valid_flight` pins this
- **SAS blocks split on *parseable* dates, never on everything date-shaped** (`sas.extract_bs4`). Its `date_re` accepts "<1-2 digits> <word> <4 digits>", and SAS flattens a leg to `... ( 1h 40m ) Avgångsterminal 5 SK 2601 | Canadair ...`, where **"5 SK 2601" matches perfectly** — 5 the day, SK the month, 2601 the year. Splitting there stranded the route and times in one block and the flight number in the next, so neither could build a leg and the whole itinerary vanished with no error. It needs *both* a four-digit flight number (SK 525 is too short for `\d{4}`) and **no arrival terminal** (with one the text reads `5 - Ankomstterminal 2 SK 2601`, and the digit beside the flight number is the terminal), which is why it survived unnoticed — exactly one email in the corpus hits it, and its legs happened to be recorded elsewhere too. The fix filters the matches through `parse_flight_date` before splitting rather than tightening the regex with a month list: that function is already the multilingual authority on what a date is. `test_sas_false_date_split.py` pins both the fix and the trap itself
- **Norwegian's "Travel documents" template has two renderings and `norwegian._flight_block_re` reads both.** The 2019 one is a field per line (`DY4371` / `-` / `14 Aug 2019` / `17:10` / `Stockholm-Arlanda`); from 2023 the dash sits on the flight-number line and the time is glued to the place (`D82603-2024 jul 29` / `07:45Stockholm-Arlanda`). The newer shape matched the rule and the marker and yielded nothing for three bookings — a miss with no error, which is why the corpus coverage script is the check, not the log. Two smaller traps sat behind it: the Swedish market writes Swedish exonyms, and `resolve_iata("Helsingfors")` was `''` (migration 0033 adds the Nordic set; "Köpenhamn" was already in 0022), and the shared booking-reference regex matched the *inside* of "hotellbokning" in the marketing block and returned the hotel's name (`CABINN`) as the PNR — the labels are now `\b`-anchored and the Swedish "BOKNINGSREFERENS ÄR:" form is read first. The passenger list is `SURNAME/FIRST` under a "Passagerare" heading, which the shared heuristic matched *inside* ("passager" + "are"), so the extractor reads it itself
- **Austrian's booking confirmation must be read before `_extract_confirmation` gets the text** (`austrian._extract_booking_confirmation`, gated on the "Itinerary details" heading). The check-in pattern there is "two IATA codes, then an OS number within 200 chars", and the confirmation's *Booking overview* prints `ARN / VIE / … / OS317` — the outbound route followed by the **return** flight number. It only failed to emit that wrong leg because no "dd Mon yy" date happened to be in the text; `test_austrian_parser.py::TestAustrianBookingConfirmation::test_the_overview_never_reaches_the_checkin_pattern` adds one and asserts the right two legs still come out. The per-leg details block has both times and both terminals, so the overview is not read at all. The rebooking mail ("Your Travel Confirmation") prints its From and To cells as **one phrase**, `Vienna Intl Stockholm Economy`, and `_route_from_confirmation_row` splits it only where the text marks the boundary (after `Intl` / `Airport`) — cutting one word early gives `Intl Stockholm`, which resolves to Stockholm *Västerås*, a real airport 100 km from the one on the ticket. Without a suffix every split is tried and accepted only when they all agree
- **`parsers/validation.py`** — Plausibility gate every extraction path passes through in `sync/pipeline.py`, applied **after** `apply_airport_timezones` so durations are real UTC. Prefers dropping a leg over storing a wrong one; every drop is logged with its reason. Note what it *cannot* do: a wrong-but-ordinary leg (right airports, plausible duration, wrong direction or wrong year) sails through, which is why extraction is kept structural rather than leaning on this gate to clean up guesses
- **`parsers/cancellations.py`** — Two record shapes for "this is no longer happening", and the reason there are two: SAS, Lufthansa and Finnair confirm that a *booking* is off and name only its reference, while Austrian announces that one *leg* is off and names the flight number and date. Neither collapses into the other — a booking reference covers legs the mail never lists, and a leg cancellation must not take its siblings with it (a cancelled OS318 out of Stockholm says nothing about the return). An airline opts in by exporting `extract_cancellations`; `builtin_rules._resolve_cancellation_extractor` binds it the same dynamic way `extract` and `extract_boarding_pass_details` are bound, so adding one needs no change there. Until this existed, cancellation was handled purely by *suppressing* extraction (`austrian.extract` returns `[]` on a cancellation subject, `finnair.extract` bails on its cancellation notice) — which stops a dead leg being created and does nothing about the leg already stored from the booking confirmation weeks earlier. Six corpus mails matched a rule, produced nothing, and left six phantom flights. **The SAS marker is past tense on purpose**: SAS's *schedule change* mail carries the same booking reference and the words "Cancel your booking" as one of three options being offered, and reprints no itinerary at all — matching "cancel" there would strike off a trip still going ahead with nothing left to restore it. `test_cancellations.py::TestSas::test_a_schedule_change_is_not_a_cancellation` pins that, and `tests/flight-cancellations.spec.ts` drives it end-to-end through `/api/sync/upload-eml`
- **A cancellation marks; it never deletes** (`sync/pipeline.py::_apply_cancellations`). `status = 'cancelled'` is reversible, visible and keeps the trip's history honest; a delete is none of those, and it would break the same "imports create and never delete" rule `sync/stays_import.py` follows. Two guards are load-bearing. (1) **A cancellation older than the flight it names is ignored** — an airline that cancels and rebooks often reissues under the same PNR, so a stored leg whose `email_date` is *newer* describes the rebooking; this is the same "newer email wins" rule `_process_emails` already applies to a restated itinerary. A flight with no source email (typed by hand) fails that comparison and is cancelled, which is correct. (2) The lookups filter `status != 'cancelled'`, which is what makes re-reading the mail on every incremental sync a no-op — a cancellation email is never marked processed, because it creates no flight
- **A schedule change is three different mails, and the pipeline treats them as three things** (`sync/pipeline.py::_record_reschedule`, `_apply_schedule_change_notices`; migration 0034). (1) A change that *reprints the itinerary* (TAP "Reservation Change", Lufthansa "alteração de reserva") has always overwritten the stored leg through "newer email wins" — right data, silently. `_record_reschedule` now runs beside `update_synced`: when either instant moved, the **previous** pair goes into `rescheduled_from_departure` / `rescheduled_from_arrival` (previous, not original — a notification reports the move that just happened), `rescheduled_at` takes the mail's date, and the traveller gets an in-app + push notification under the `delay_alert` preference, deduplicated by `already_sent` on the *new* departure so a rescan cannot notify twice while a second move can. (2) A change that moves the *date* never matched `find_by_number_and_date` — the date is its key — so the leg was created beside the old one. `FlightRepository.find_moved_leg` joins on flight number, both airports **and** booking reference within ±3 days, and only when all four agree; a leg with no reference never matches, because a wrong join here overwrites a real flight with another's times. (3) A *notice* that names the booking and prints no itinerary (SAS: "we've had to change our flight schedule which has impacted your trip with booking reference X") can update nothing. An airline opts in by exporting `extract_schedule_changes` (bound like the other three hooks); the pipeline stamps the booking's non-cancelled legs with `schedule_change_notice_at` and notifies. Two guards make a rescan a no-op: a leg whose own email is *newer* than the notice was already re-read from the itinerary the notice points at, and a leg already stamped with this notice is skipped. A later itinerary that moves the leg clears the stamp. The frontend reads both through `utils.isFlightRescheduled` / `hasScheduleChangeNotice` — amber "Rescheduled" badge on `FlightRow` until the flight has flown, and a banner with the previous times on `FlightDetailPage`, kept *outside* the live-status chain because a rescheduled flight can still be on time. `tests/sync/test_schedule_changes.py` drives all three through `_process_emails`; `tests/flight-reschedule.spec.ts` does it over `/api/sync/upload-eml`. Found on the way: the shared booking-reference regex's "receipt J9CRT8" rule let its whitespace cross a newline, so a receipt headed `ELECTRONIC TICKET RECEIPT` followed by `BOOKING REF:` returned "BOOKING" as the PNR — now same-line only
- **Cancelled flights are excluded from Stats** (`stats/repository.py`), and the filter is written `(f.status IS NULL OR f.status != 'cancelled')`. The `IS NULL OR` is not defensive noise: the column is nullable and in SQL `NULL != 'cancelled'` is NULL, which is falsy — a bare `!=` would silently drop every flight whose status was never written, turning a filter into data loss. `test_stats_repository.py::TestCancelledFlightsAreNotStatistics::test_a_null_status_is_still_counted` pins it. Without the exclusion a cancelled leg still contributes its distance, its CO2 and both airports' countries, and — worse — sits between the two halves of a connection and breaks the adjacency the 24h layover rule walks, exactly as the duplicate legs `_dedupe` exists to collapse did
- **The frontend reads `status` *and* `live_status`** (`utils.isFlightCancelled`, used by `FlightRow` and `FlightDetailPage`). They mean different things: `status` is the authoritative state an airline's cancellation email writes, `live_status` is what the AviationStack tracker last reported. The UI read only the latter, so a flight the airline had cancelled in writing still rendered as an ordinary leg — and on an install with no AviationStack key nothing would ever have said otherwise. Deliberately **not** folded into `flightStatus`, which answers a different question (where the flight sits in time) and is derived from the two timestamps alone — a cancelled flight still has a departure in the past
- **`parsers/car_rental.py`** — Hertz, Sixt and Europcar confirmations, structural and gated on the sender exactly like an airline rule. No generic tier, for the same reason `generic_html.py` was deleted: a rental mail is mostly price breakdown and terms, and anchoring on "a date near the word pickup" across an unknown template invents bookings. All three vendors lay their fields out one per line in the **plain-text** part, so the extractors walk lines rather than matching one regex — the filler between fields is independently optional in all three, and a regex with optional filler drifts onto the next block's values as soon as one piece is missing (the trap `pegasus` documents). Times come back as *naive local* ISO strings; this module never guesses a timezone, because the counter's address is the only evidence and resolving it is the importer's job. The one judgement call is `_numeric_dates_month_first`: **Europcar prints "8/24/19" with no month name to settle the order**, and guessing wrong moves a booking by months rather than failing visibly — so the two dates in one mail (from one template) settle each other, a middle component above 12 meaning month-first and a leading one meaning day-first, and only a mail where *neither* date disambiguates falls back to month-first, logged
- **No generic extraction tier — on purpose.** There used to be one (`parsers/generic_html.py` plus a generic PDF regex): anchor on any flight-number-shaped token, then scan nearby lines for airports/times/dates. Measured across a 372-email corpus, *every* leg it was the sole source of was wrong or incomplete — a Ryanair round trip with both legs pointing the same way, a TAP receipt reading the `NVA` not-valid-after label as Neiva, e-tickets dated a year off, LATAM round trips missing the return, Lufthansa itineraries reduced from six legs to one. Each airline template it had been covering is now read by that airline's own rule (see `test_airline_rule_coverage.py`), which yields *more* legs than the scanners did, correctly. If a new email format shows up unparsed, add a rule for it or let the LLM take it — do not reintroduce a proximity-guessing tier
- **`parsers/builtin_rules.py`** — Airline rules keyed to `PARSER_VERSION = '34'`; supported: LATAM (LA), SAS (SK), Norwegian (DY), Azul (AD), Lufthansa (LH), British Airways (BA), ITA Airways (AZ), Kiwi.com, Ryanair (FR), Austrian Airlines (OS), TAP Air Portugal (TP), Finnair (AY), Wizz Air (W6), Brussels Airlines (SN), Iberia (IB), Vueling (VY), Qatar Airways (QR), Turkish Airlines (TK), Pegasus Airlines (PC). `SUBJECT_PATTERN` gates every rule after the sender matches, so a missing keyword there silently disables an airline — "Resehandlingar" was the reason Norwegian's travel-document mails reached no rule at all; `ticket` had to be added there for Turkish Airlines, whose subject is just "Turkish Airlines - Ticket Details", and `rezerv` for Pegasus, because `reserv` does not match the Turkish "Rezervasyon"
- **`sync/grouping.py`** — Auto-groups flights into trips by booking reference, then 48h time proximity
- **`sync/stays_import.py`** — Decides which trip an imported booking belongs to, and opens one when nothing fits. The accommodation counterpart of `grouping.py`, beside it for the same reason: what a booking belongs to is a sync concern, not something `stays/` should know. **The rule was measured, not guessed.** Against nine years of real mail (6 bookings, 74 flights) a stay matches the trip whose flights fall inside its *own* span — the traveller flies in on the check-in day and out on the check-out day — plus `STAY_TRIP_WINDOW_DAYS` of slack. Five of six found exactly one trip, and the answer was identical at every window from ±0 to ±21; only at ±30 did a stay start touching two. The window is therefore deliberately tight: slack buys nothing ±0 did not already find, and every extra day is a chance to swallow a neighbouring trip. **Bracketing was considered and dropped** — the intuition that a stay sits *between* an outbound and a return does not match real itineraries, where the flights are inside the stay. The **country gate** (the markup's `addressCountry` against `airports.country_code`) never once blocked a true match and is what stops a Lisbon weekend being absorbed by a Tokyo trip straddling the same fortnight. What it cannot do is **remove** a booking: no cancellation or alteration mail appeared anywhere in the corpus, and in the one case where a booking was clearly cancelled and rebooked the only evidence was a second confirmation for the same nights at a different property — so imports create and never delete, and two overlapping stays is a visible row rather than silent corruption
- **Grouping reuses a stay-created trip rather than building a second one beside it** (`grouping._find_stay_trip_for_flights`). Accommodation is routinely booked before the tickets — two of the six measured bookings were confirmed four and seven months ahead of their flights — so by sync time there may already be a trip built from the hotel alone, with a name, a cover photo and whatever has since been hung off it. The lookup is the same move `_create_trip_for_flights` already makes for a known booking reference, and its test **mirrors `stays_import._find_trip_for_stay` exactly**, because a booking that finds a trip in one direction must find it in the other. Only flightless auto-generated trips are eligible. Note this is why `_create_trip_for_flights` now calls `recompute_span(..., include_airports=False)` after assigning flights: the trip it is joining may hold a stay whose nights fall outside the flights' range, and writing the flight-derived pair straight in cropped the stay out of its own trip's span. `include_airports=False` is load-bearing — `_find_trip_destination` has already named the destination better than the span recompute can, which on a round trip would overwrite it with the final arrival, i.e. the traveller's own origin
- **A booking reference belongs to a leg, not to a trip.** `trips.booking_refs` is written by auto-grouping and read back by it — but *every* grouping read is gated on `is_auto_generated = 1`, so on a trip you created by hand the list did nothing at all except make the reference searchable. Both trip forms therefore stopped asking for it; the column stays, because auto-grouping still depends on it to find the trip a newly-synced booking belongs to and to reuse its id (which preserves the cached cover image). To keep search working, `get_search_index_rows` now concatenates `flights.booking_reference`, and `get_segment_booking_refs` is a **separate** bulk query for the ground legs' references — the flight index is `FROM flights`, so a rail-only trip produces no row there to join onto.
- **`TripService.place_columns` takes the DTO *or* a plain mapping**, and must keep doing so. The two routes hand places over in different shapes: create passes the `PlaceFieldsDTO` through, while update goes via `body.model_dump(exclude_none=True)`, which turns nested models into dicts. Assuming the object form crashed **every** trip edit with a 500 — the edit form always sends both places, so it was never only the field being edited that broke.
- **Shortening a trip past its own legs is advisory, not an error.** The span is the declared dates unioned with the contents, so that end simply does not move — which from the form looks like a save that did nothing. `EditTripPage` loads the trip's segments and stays (flights ride along on the trip) and computes the span the contents need, then names those dates in a `.form-warning` when the chosen pair falls inside it. It never blocks: editing the trip first and fixing the leg afterwards is a legitimate order, and the lookup failing means no warning rather than no save. Dates are compared as **local calendar dates at each end** — a 01:00Z arrival is the previous evening in São Paulo, and a UTC comparison would warn on the wrong day.
- **A trip has two spans too, for the same reason.** `start_date` / `end_date` are derived by `_recompute_span` as MIN/MAX over the trip's flights, segments and stays — **unioned with** `planned_start_date` / `planned_end_date` (migration 0028), the pair the trip form actually writes. Without that union a hand-made trip's span collapses to its first leg's day the moment that leg is added, which is exactly the state in which someone goes to add the *return* leg: it would already fall outside its own trip. Unioning means the derived span can only grow past what was declared, never shrink inside it; editing the trip's dates is the one way it shrinks, which is why `update_trip` calls `recompute_span` whenever the declared pair changes. An empty date field must reach the column as NULL, never `''` — `MIN('', '2026-12-31')` is `''`, which drags the span back to the beginning of time. Auto-generated trips declare nothing; they only have contents.
- **`AddTransportPage` bounds every date field with that span** (`min` / `max`), and both bounds are **date-granular** — `T00:00` and `T23:59`, never the real instants. A bound carrying a time makes the boundary day's other hours invalid and browsers express that by greying the whole day out, so the day you actually travel on reads as disabled; this is the same rule, and the same trap, as `TripStays`' `checkOutMin`/`checkOutMax`. The ceiling is suppressed when it would fall before the floor (min > max greys out the *entire* calendar), a failed trip lookup leaves the pickers unbounded rather than blocking the form, and the range is stated in words on the page — a greyed calendar with nothing explaining it has twice been reported as a bug.
- **A trip goes to several places** (migration 0029, `trip_destinations`). The origin stays one column-set on `trips` — a trip starts where you start — but the far end is a list, ordered, one row per place with its own coordinates and country code. A row per place is what lets each destination count as a country visited; a JSON list on `trips` would have made that string-parsing in SQL. The single `destination_*` columns from 0027 were backfilled into the table and dropped: keeping them as a mirror of "the first one" would be two sources of truth for the same fact. `destination_airport` is untouched — derived from the flights, answering a different question. `set_destinations` replaces the list wholesale rather than diffing, because the order is part of what the user chose.
- **`EditTripPage` seeds the city fields from the trip's airports** when they are empty and the trip has a derived airport pair. A trip built from email knows exactly where it went and had nothing typed, so the form opened blank on precisely the trips that already had the answer. The seed goes into the **form**, not the database: it is offered as a filled-in default and saved only if the traveller saves, and anything they already typed is left alone (the airport lookup is not even issued in that case). The airport row carries coordinates and a country, so the seeded place is complete rather than a bare label — the country is the airport's, which is a fact rather than a guess. A failed lookup leaves the field **empty**: an IATA code in a field that asks for a city is worse than blank. `trips.route_seeded` says where the values came from, because a field that fills itself is otherwise indistinguishable from one you filled and forgot.
- **The cover photo picks a destination at random** (`TripImageService._resolve_destination_city`), so "find a different image" on a multi-stop trip moves between its cities instead of re-rolling photos of the first one. The typed destinations win over the destination airport's city, which wins over the last flight's arrival.
- **`TripCard` prints the first destination and a count** (`São Paulo +1`). The bag-tag line stays one line high whatever the trip does; the full list is on the trip page.
- **`EditTripPage` no longer offers a destination airport.** It existed only to pick the cover photo's city, which the destinations now do.
- **A trip's destinations count toward visited countries** (`stats/repository.py::list_ground_countries`), gated on the trip having finished — a country you plan to visit is not one you have. They are often the only record of a country on a trip that was driven.
- **A trip's ends are two different facts.** `origin_airport` / `destination_airport` are **derived**: `_recompute_span` rewrites them from the trip's *flights* on every mutation and nulls them when there are none, so nothing typed can survive there and a trip that is driven or ridden has no ends at all. Migration 0027 adds the **user-owned** pair — `origin_place` / `destination_place` plus `_lat` / `_lon` / `_country` on each — which nothing recomputes. Both trip forms ask for these as **cities** through `PlaceInput kind="city"` (`GET /api/cities/search`, registered on `trips/routes.py`'s own `cities_router` because the prefixed router cannot serve `/api/cities/...`). `TripCard` prefers the typed end over the derived one **per end**, so a trip flown out and driven back still prints both. The country comes from the geocoder result the user picked, never inferred from coordinates — same rule, same reason, as migration 0025.
- **The cover photo's subject is the typed destination first** (`TripImageService._resolve_destination_city`), then the destination airport's city, then the last flight's arrival airport. That ordering is what finally gives a rail or road trip a photo: the Wikipedia lookup could only ever resolve an IATA code. `EditTripPage` still offers the destination *airport* underneath the city pair, for a flown trip whose photo you would rather pick by airport.
- **`car` searches settlements, not stations.** It had no `_OSM_TAGS` entry at all, so it fell through to `_ALL_TAGS` — the every-station fallback — and typing "Florianópolis" for a drive offered bus stops and street names with the city nowhere in the list. A drive has no station; its ends are cities, or an address when it starts at a door, so `car` shares the `place` tag and the settlement filter with `city` (`_CITY_KINDS`) **and** the untagged second pass with `stay`. The exception lives in `search_stations` rather than a new endpoint because the picker sends whichever segment type it is editing. `PlaceInput.label` gives a car's settlement rows the same region+country line a city gets, while its address rows keep their address line.
- **The city query asks for the whole `place` key and filters on the way back** (`_SETTLEMENT_VALUES`). Filtering the *query* to `place:city|town|village` is the obvious thing and finds nothing: **Brazil maps its cities as `place:municipality`**, so "Florianópolis" matched no tag at all and returned zero results, and Norway does the same (Oslo's node is a municipality under a county). Photon already ranks the real settlement first, so the fix is to keep `city|municipality|town|village|borough` and drop the rest — hamlets and farms (four "Florianópolis" hamlets), localities, islets, and the administrative wrappers (state, region, county) that share a city's name. Suburbs and neighbourhoods are excluded on purpose: a district of a city is not the city. The city fetch also over-fetches **8×** rather than 3×, since the filter discards most of a `place` key's hits.
- **Photon returns the same node twice under different labels**, and both halves of the defence must stay. Querying "Rio de Janeiro" gives Itaboraí once as its own city and once with the *state* as its city, at byte-identical coordinates — `_collect`'s `(name, city)` key let both through. So `_collect` now also collapses on the exact `(lat, lon)` point, and `PlaceInput`'s list is keyed on the **index**, not the coordinate pair. The visible symptom was two identical rows; the real one was the page vanishing behind `App.svelte`'s error boundary ("This page didn't load."), because a duplicate key is a hard error in Svelte. Keep both: the server fix is the correct data, the index key is the half a third-party geocoder cannot re-break.
- **A city's dropdown line is region + country, not its address** (`PlaceInput.label`). Photon's `address` for a city is the city itself — "Oslo" under "Oslo", which distinguishes nothing — while Oslo, Minnesota reads "Marshall", its county, with no hint of the country. The region is dropped when it merely repeats the name.
- **`photon.search_places(kind="city")` overrides the result category.** Every hit is a populated place by construction, but OSM's `place` key is also how a street-like feature is tagged, so the shared classifier would file them all as addresses and put a divider above every row of the city picker. `_PLACE_KEYS` itself must **not** gain `"place"` — the stay picker depends on those landing under "Addresses", and a test asserts it.
- **Outbound/Return detection** (`utils.splitLegs`) keys off the flights themselves — last arrival airport equals first departure airport — *not* `trip.origin_airport` / `trip.destination_airport`. Those two disagree about their meaning: `_recompute_span` sets destination to the **final** arrival, which on a round trip is the origin, so the old `origin === destination → don't split` guard meant a real FRA→PEK→FRA trip never split — the one case the split exists for. Note the same mismatch still affects the Wikipedia destination photo, which looks up `destination_airport`
- **`trash/` and `activity/`** — Deleting a trip or a flight is a *real* delete that first snapshots the row and everything reachable from it into `trash` (migration 0035), and every destructive or structural action is written to `activity_log`. Both exist because a trip with a rating, notes and expenses vanished from a real install and nothing could say when or how — and, worse, could not come back: the mails behind its flights stayed in the processed-mail ledger, so no sync would ever re-read them. Three decisions are load-bearing. (1) **The snapshot walks the schema, not a list** (`trash/snapshot.py::collect_graph`): every table's `PRAGMA foreign_key_list` says what it points at, and a table joins the graph when it points at one already in it, starting from `trips` (or `flights`). Composite keys are matched as tuples; anything pointing at `users`/`sessions`/`guests` is never followed, because an account is not part of a trip. A child table added next month is included without a change here. (2) **The live rows are still deleted.** A `deleted_at` column would have needed a guard at every one of the ten-odd modules that query `flights` directly, and the first missed guard feeds a deleted leg into Stats or the aircraft sync. Deleting for real keeps every read path correct, and — the reason people delete in this app — frees the unique key on `flights.email_message_id` and drops those mails from the ledger (`SyncRepository.forget_emails`), so a mis-parsed booking can be deleted and re-imported with a better parser and come back as fresh rows. (3) **Restore never clobbers**: rows go back with INSERT OR IGNORE, parents first, only the columns the current schema still has; anything re-created meanwhile is reported as *skipped*. A restored flight whose trip is gone comes back ungrouped for the next grouping run. The cover image and document files stay on disk until the trash entry is purged. `TripService.delete_trip` / `FlightService.delete_flight` call `trash_service`; merges only log. **Re-group is no longer exposed** — `POST /api/sync/regroup` and its Settings button are gone (see `sync/grouping.py::regroup_all_flights`): it deleted every auto-generated trip to fix what is nearly always one trip's grouping, and a trip row's deletion takes its rating, notes, expenses, budget, stays, segments, car rentals and Immich link with it by foreign key. The per-trip repairs (`merge_trip`, `ungroup_flight`) do the same job without collateral, and `_merge_overlapping_groups` already re-merges trips that should be one on **every** sync, which was regroup's main justification. Note it is the `DELETE FROM trips` that destroys data, not the grouping: `_create_trip_for_flights` already updates a matched trip **in place**. The function is gone with it (git history has it), along with the `_reuse_ids` map that existed only to serve it; what survives is the live `booking_refs LIKE` lookup, which is the half that reassigns flights without replacing the trip. `test_api_sync.py::TestRegroupIsNotExposed` fails if the route comes back
- **Full sync clears the processed-mail ledger, and a PARSER_VERSION change forces one rescan** (`SyncRepository.reset_last_synced`, `pipeline.run_email_sync_for_user`). The ledger only ever saved a re-parse: duplicates are refused by the unique key on the source mail. Keeping it across a full sync meant the sync re-fetched mail it then refused to look at. The rescan is the one the `PARSER_VERSION` comment always promised: nothing read that constant outside its own file, and `email_sync_state.parser_version` (designed into the baseline schema, lost when the table was rebuilt, re-added in 0035) was never written. Now the first sync after the version changes looks back the full `first_sync_days` window with `skip_dedup=True` and records the version on completion; everything downstream is idempotent (unique mail key, newer-email-wins, fill-only-empty enrichment, stamped cancellations and notices). `tests/sync/test_rescan.py` pins the window and the one-off-ness
- **`auth/`** — Session cookies (itsdangerous), bcrypt passwords, TOTP 2FA, audit logging (`audit_log.py`), and the per-user display preferences (`locale`, `accent`) that ride on `/api/auth/me`; also re-exports cross-cutting authorization helpers (`get_current_user`, `can_access_trip`, etc.) imported as `from ..auth import ...` throughout the backend
- **The announcement banner is permanent on a demo** (`AnnouncementBanner.svelte`, fed by `MeResponseDTO.demo`). Everywhere else it is a notice the reader can dismiss, keyed in sessionStorage on the announcement's own text so a *changed* announcement comes back. On a demo it is not a notice but a standing fact about the install — everyone shares one account — so it renders with no dismiss button and ignores any earlier dismissal, falling back to the localised `demo.banner` string when the deployer set no `ANNOUNCEMENT` of their own. Note the banner is only as fresh as `/api/auth/me`, which the SPA reads at boot and at sign-in and never again; the service worker is *not* the staleness here — `/api/auth/*` is network-first in `sw.js`
- **The login page's one unauthenticated read is `GET /api/auth/public-config`** (`auth/routes.py`, on `middleware.ALLOWED_UNAUTHENTICATED_PATHS` beside `/login` and `/me`). Server config the *signed-in* app needs rides on `/api/auth/me`; that response 401s in exactly the state the login page is rendered in, which is why the demo credentials need an endpoint of their own rather than a field there. It publishes the `DEMO_USERNAME` / `DEMO_PASSWORD` pair **only while `DEMO_MODE` is on** — off (the default) it answers three empty fields, so configuring the credentials is not by itself consent to publish them and no ordinary install ever advertises a working password. `LoginPage` renders the notice from that response alone: deliberately no hostname check and no build-time flag, because the Docker image is built before any deployer has a demo host — the same reason `CARTO_API_KEY` is not a Vite var. The fetch sits in a bare `catch`, since the sign-in form is the feature and the notice is decoration: a server too old to know the route must not take the page down with it. `test_api_auth.py::TestPublicConfig` pins both states, including that the password is absent from the response body with the flag off, and `tests/demo-login.spec.ts` asserts the page and the endpoint agree whichever way the server under test was started
- **`scripts/reset_demo.sh` + `scripts/seed_demo.py`** — the public demo's six-hourly wipe-and-reseed, run from cron on the host (not by the app). The wipe is expressed as a **KEEP list** (`alembic_version`, `airports`, `airport_aliases`, `aircraft_types`, `global_settings`, `non_flight_domains`) and deletes every other table, because the wipe list it replaced went stale exactly as you would expect: written when trips, flights, documents, day notes, shares, sessions and users were the whole app, it was by 0036 deleting the trip row and **orphaning** its expenses, stays, segments, car rentals, budgets, guests, packing items, destinations, notifications, push subscriptions, trash and activity log. Nothing cascaded either — the child tables do declare `ON DELETE CASCADE`, but SQLite opens every connection with `foreign_keys` **OFF** and this standalone script (unlike `database.py:30`) never turned it on, so those rows survived every reset and accumulated. The pragma is still deliberately left off: switching it on makes `DELETE FROM users` fail against the `NO ACTION` references (`flights`, `trips`, `trip_segments`, `trip_stays`, `trip_car_rentals`, `email_sync_state`), so a complete list beats an ordering puzzle. `seed_demo.py` recreates the account through `POST /api/auth/setup` — which is why that route is *not* among the demo refusals, and why the demo account is an **admin** — and reads `DEMO_USERNAME` / `DEMO_PASSWORD` from the environment so the seeded account and the credentials the login page publishes cannot drift
- **Demo mode is a set of refusals, not a UI mode** (`auth/access.py::refuse_on_demo`, exported through `..auth` like `can_access_trip`). A demo account's password is published, so every visitor is that account: one of them enabling 2FA puts a code only their phone can produce in front of every later sign-in, changing the password invalidates the one printed on the login page, and creating, editing or deleting accounts does both at once — each recoverable only with shell access to the server. So `POST /api/auth/2fa/enable`, `POST /api/auth/change-password` and all three writes on `/api/users` return **403** while `DEMO_MODE` is on. The guard is in the routes because the hidden frontend control is a courtesy and `curl` does not read it; `SettingsPage` and `UsersPage` hide those controls from `$currentUser.demo` so nobody fills a form only to be refused. **2FA *disable* is deliberately still allowed** — it is the escape hatch, and on an account whose password is public it hands an attacker nothing. Listing users stays allowed too: reading who exists changes nothing
- **A demo's sign-in throttles are relaxed, not removed** (`auth/routes.py::_login_rate_limit`, `AuthService._check_login_lockout`). Both defences are keyed on IP: slowapi's 5/minute and a five-failures-in-ten-minutes lockout. On a demo that is exactly wrong — everyone arrives with the same published username, and behind a reverse proxy they share one apparent address, so the sixth visitor in a minute was refused for being sixth. Demo mode raises the route ceiling to 120/minute (a bound a crowd cannot reach still bounds a script — this is why it is not simply exempted) and skips the lockout, recording no failures either, since the pruning that keeps that list bounded lives in the check being skipped. Rate limiting is stubbed out across the test suite, so `_login_rate_limit` is asserted directly while the lockout is driven through the API
- **`smtp_server.py`** — aiosmtpd inbound SMTP on port 2525 for email forwarding
- **`utils/`** — Generic, dependency-light helpers with no DB access, used across every feature: `dates.py` (flight-number validation, ISO datetime conversion, duration/status calc — re-exported from `utils/__init__.py` for import-path stability), `text.py` (`fold_text` — accent folding, shared by airport name resolution and the CSV loader that writes the folded columns), `i18n.py` (minimal backend translations reusing the frontend's locale JSON files — resolved from `$LOCALES_DIR`, then `frontend/src/locales/` for a repo checkout, then `backend/locales/`, which the Dockerfile populates from the same files because the image ships only the *built* frontend. An unresolved key falls back to the key itself, which reaches users as a raw `notif.*` string in a push notification, so a missing locale file is logged at error level rather than silently)
- **`airports/`** — `repository.py` (AirportRepository: search + IATA lookup + CSV bulk-load-if-empty seeding, plus `backfill_rank_columns()` / `seed_aliases_from_keywords()` — run at startup from `main.py` — which populate the `type` / `scheduled_service` ranking columns, the accent-folded search columns, and exonym aliases derived from the CSV's `keywords`; curated aliases from migration `0022` deliberately outrank those. The backfill downloads `airports.csv` when absent (`_ensure_csv()`), because `data/` is a mounted volume and an upgraded instance typically has a populated table but no CSV. Completion is recorded in `global_settings` under `airport_rank_backfill_done` rather than inferred from the data — a few stored airports are retired upstream and keep a NULL `type` forever — and the flag is only set when the CSV pass actually ran, so an instance that was offline at upgrade time retries on its next start) + `routes.py` (`GET /api/airports/search`, `GET /api/airports/{iata}`) + `timezone.py` (converts naive local flight times to UTC using airport coordinates + TimezoneFinder — lives here rather than in `utils/` because it touches the DB, and not in `flights/` because `parsers/` needs it too and parsers/flights are kept independent). Lighter than the full routes→service→repository layering since there's no business logic in the routes. Other packages still query the `airports` table directly for their own narrow needs (parsers/, sync/grouping.py, trips/, settings/) rather than going through this repository.
- **`segments/`** — Manually-added non-flight transport legs (train, bus, ferry, car) on a trip: full routes→service→repository layering over the `trip_segments` table, plus the `GET /api/stations/search` type-ahead endpoint. Deliberately a **separate table from `flights`**, not a `transport_type` discriminator on it — `flights` carries ~15 flight-only columns and ten backend modules query it directly, so a discriminator would need a `WHERE type = 'flight'` guard at every one of those call sites and the first missed guard feeds a bus into `integrations/aircraft/sync.py`. Places are a free-text label plus **optional** coordinates rather than an IATA code (stations are not in the `airports` table); nullable coordinates are what let a hand-typed place still save, at the cost of its map line and timezone conversion. Times are stored UTC like flights, but the zone comes from the station's coordinates via `airports.timezone.get_timezone_for_coords` rather than from an airport lookup. `service.update_segment` merges a PATCH onto the stored row before validating — `_build_values` always emits a full row, so without the merge a one-field PATCH nulls everything else *and* skips validating the changed end against the unchanged one. The `type` column has no CHECK constraint, which was left open for accommodation (`stay`) to join later — that is *not* what happened: stays got their own `trip_stays` table (see `stays/` below) because a stay is one place and a span, not two places and a direction
- **`stays/`** — Accommodation on a trip (hotel, airbnb, hostel, other): full routes→service→repository layering over the `trip_stays` table. A **separate table from `trip_segments`**, even though migration 0023 deliberately left `type = 'stay'` available by omitting the CHECK constraint — that kept the option cheap, it did not make the shape fit. A segment is two places and a direction; a stay is one place and a span, so reusing it would mean `departure_place` and `arrival_place` holding the same string, `TripMap` drawing a dashed line from a point to itself, `duration_minutes` in the wrong unit, and a `type !== 'stay'` guard in `splitTransport`/`SegmentRow`/every other segment consumer — the same "first missed guard" argument 0023 used to keep buses off `flights`. `check_in_date` / `check_out_date` denormalise the **local calendar date at the property** next to the UTC instants and are load-bearing three times over: SQLite cannot convert timezones, so `_recompute_span` would read the wrong day for a property far enough west (15:00 local at UTC-10 is 01:00Z the *next* day); a booking's identity genuinely *is* its local dates; and the day planner bands a stay across days off those strings without doing timezone maths in the browser. `service._build_values` merges a PATCH onto the stored row before validating, for the same reason `SegmentService` does. Validation is deliberately thin — a stay is **not** required to fall inside the trip's dates, because the span is derived from the trip's own contents (circular) and because the airport hotel booked for the night before an early departure is a real booking; stays *extend* the span instead, and only a check-out at or before check-in and a stay over 365 nights (a mistyped year) are hard rejections. `TripStays.svelte` adds two blocks of its own on top, both client-side: a check-out at or before check-in, and a check-out later than the trip's last transport. Both disable Save *and* render the reason next to the form. The check-out picker additionally carries `checkOutMin` — **midnight on the check-in day**, deliberately not the check-in instant: a min carrying the 15:00 check-in time makes that day's earlier hours invalid, and pickers express that by greying the whole day, so the boundary day reads as broken. Date-granular min greys out the days before; the ordering block catches the same-day-earlier case with a message. Greyed-out days here have twice been reported as a broken picker and were correct both times, so check that the dates being tried are not simply earlier than check-in before touching this. `checkOutMax` is the mirror image — end of the last travel day (`T23:59`, so checking out the morning you fly home still works) — but it is **suppressed whenever it would fall before the floor**: min > max greys out the *entire* calendar, and an inverted range is reachable in ordinary use (a one-way flight out, return not added yet, check-in after it). `afterTravel` still reports that case in words
- **A trip's guests are a roster, not an inference** (`trip_guests`, migration 0036). Membership used to be *derived* — `GuestRepository.list_for_trip` asked which guests some expense on the trip already named. That scoped guests correctly (a guest from a 2024 city break is not a suggestion on an unrelated 2026 trip) but made the roster a consequence of the expenses, and left a dead end with no error in it: a guest created in Settings was in no payer select and no split-between list, because no expense named them, and no expense could name them because they were in no list. Three guests were added on a real install and none could be used. The table states membership instead; the migration backfills it with **exactly** what the old derived query returned, so no install changes shape. Two guards keep it consistent with the expenses: `ExpenseService._join_guests_to_trip` puts any guest an expense names onto the roster as it writes (which is what still lets one quick-added in the expense form be used immediately — `_acceptable_choices` validates against `list_mine`, not the trip), and `remove_from_trip` refuses with a 409 while an expense there still names them, the same rule that stops a guest being deleted outright. Deliberately no `added_by`: a guest belongs to the trip, not to whoever typed them in, and any collaborator can manage the roster for the same reason any of them can add an expense. `TripPeople.svelte` is where it is managed — in the **spine**, not the aside, because the roster is what bounds the expense pickers — and it is the **only** place a companion is added: the expense form's own "add guest" box and its suggestion strip over the whole address book were removed with it, on the same "a second door to the same room" grounds that give `AddTransportPage` one entry point. Note its locale keys are `trip_people.*`, **not** `people.*` — that namespace already belongs to `PeoplePicker`, and since a later JSON key wins, colliding on `people.add_placeholder` silently made the section render the picker's strings; component tests cannot catch it because they mock `t` to echo the key back
- **`car_rentals/`** — A hired vehicle held over a span of a trip (migration 0032): full routes→service→repository layering over `trip_car_rentals`. A **separate table from `trip_segments`**, though `type = 'car'` already exists there — and the two are complements, not alternatives. That type is a *drive*: two places, a direction, and a duration that is time spent travelling. A rental is a contract over days, with several drives inside it or none, so reusing a segment would put four days of *not* travelling in `duration_minutes`, draw a `TripMap` line between two points nobody travelled between at those times (and for the common same-place hire, a line from a point to itself), and sort a standing contract into Outbound or Return by `splitTransport`. Same argument 0024 made for keeping stays off segments, and the same "first missed guard" cost. Unlike a stay it has **two** places, because one-way hires are ordinary — two of the three bookings in the measured corpus were one-way (Munich→Vienna, Trapani→Catania). `pickup_date` / `dropoff_date` denormalise the local calendar date at each counter for exactly the reasons `stays` does, and both ends carry their own timezone because a one-way hire can cross one. Validation is thin on the same grounds: a rental is not required to fall inside the trip's dates (circular, and a car collected the evening before the first drive is ordinary) — it *extends* the span, and only a drop-off at or before the pickup and a hire over 365 days are hard rejections. `service._build_values` merges a PATCH onto the stored row before validating, for the same reason `SegmentService` and `StayService` do. Email import lives in `sync/car_rentals_import.py`
- **`sync/car_rentals_import.py`** — Which trip a hired car belongs to. Reuses `stays_import`'s rule **widened by one term**: "contents" means flights *and stays*, where the lodging importer looks only at flights. That difference is the point of the feature — a car is hired precisely on the trips that are not built out of flights, and a flights-only rule would be blind on exactly the itineraries a rental defines. The **country gate is weaker on every side** than the stays one, deliberately: a stay's country comes from the platform's own markup, a rental's only from geocoding the counter, so a NULL on either side passes (an unknown rental country, an airport with no `country_code` recorded — which is also what a missing `airports` row looks like through the LEFT JOIN). The gate fires only when both sides know and disagree, because the failure modes are not symmetric: joining the wrong trip puts a visible row on the wrong page, while refusing a true match silently creates a duplicate trip beside a perfectly good one. Imports create and never delete, matching `stays_import` — no vendor in the corpus sends a parseable cancellation. **The pipeline runs this ahead of the blocked-domain skip**, exactly as it runs the lodging import: hertz.com, sixt.com and europcar.com are all on `_NON_FLIGHT_DOMAINS` because they never contain *flights*, and a sender-gated structural reader cannot invent a booking. `test_car_rentals_import.py::TestThroughTheSyncPipeline` asserts that ordering, and fails if the hook moves below the skip
- **`settings/integrations.py`** — Configuration status of the optional third-party integrations (CARTO, AviationStack, Photon, Ollama, web push), behind `GET /api/settings/admin/integrations` and summarised in one **INFO** line at startup. Two rules it exists to hold: a key's *value* never leaves the server (callers get `configured` plus the env var name, never the secret — there are tests asserting a secret appears in neither the response nor the log), and `PHOTON_URL` is reported with **three** states rather than a boolean, because it defaults to komoot's public instance and a naive `bool()` check would claim credit for something the admin never chose. INFO and not WARNING is deliberate: every one of these is optional and degrades a single feature, so warning about a deliberate configuration is how people learn to ignore warnings. Admin-only, because they are all server-level settings a regular user cannot act on
- **`routes/`** — Leftover pre-refactor routes not yet folded into a feature package: `version.py` (app version endpoint)
- **`integrations/`** — Third-party API clients, one subpackage per provider: `immich/client.py` (album create/check), `aircraft/client.py` (AviationStack → OpenSky → hexdb.io lookups) + `aircraft/sync.py` (background aircraft-type sync job) + `aircraft/status_sync.py` (background live flight-status sync job, also AviationStack) + `aircraft/repository.py` (AircraftTypeRepository: the local `aircraft_types` cache table, seed data, and the one-time flight-row name-normalization sweep), `llm/parser.py` (optional Ollama LLM fallback; `llm_extract_flights(email_msg)` returns validated flights or `[]` when disabled; validates IATA codes against airports DB before returning), `wikipedia/client.py` (destination photo fetch + local WebP cache), `photon/client.py` (OpenStreetMap place type-ahead for `segments/` and `stays/`, plus `reverse_country` for the one-time country backfill. Results are held in a bounded 10-minute TTL cache keyed on (query, kind, limit) — the picker fires a request per debounced keystroke against a public rate-limited service, and prefixes repeat constantly; `reverse_country` caches on coordinates rounded to ~1km, misses included, so the backfill does not retry a coordinate the geocoder cannot place. `clear_cache()` exists for tests. `PlaceInput.svelte` keeps its own per-form memo on top, which is what absorbs backspacing; `lang=en` and `osm_tag` are both load-bearing — without the former Photon answers in the local script and Latin-script queries barely match, without the latter every street sharing the name comes back. Chosen over an offline GeoNames load on coverage: GeoNames holds 669 stations in China against OSM's 17,320, and lacks Xi'an North entirely). Feature packages (trips, flights, sync, settings) call into these as clients rather than owning the third-party integration logic themselves.

### Frontend (`frontend/src/`)
- **Svelte 5** SPA with Vite; TypeScript throughout
- **Design language: airport wayfinding** (`app.css`). Three rules hold the whole surface together and are easy to break one component at a time. (1) **One accent, and the reader chooses it.** `--accent` is a single hue worn by exactly four things — a filled button, the active nav item, the trip countdown, and an *ongoing* trip — and nothing else is tinted with it. It has *three* tokens rather than one: `--accent` is the fill, `--accent-on` is what sits on top of that fill, `--accent-text` is the accent used as text on the page background. `--accent-on` is ink on some presets and white on others, so a component hardcoding `color: #fff` on an `--accent` background is broken on half the palette; that bug has already been fixed three times (`AnnouncementBanner`, `UsersPage.badge-admin`, `SettingsPage.theme-btn`), so grep for it before adding a filled control. (2) **Every other colour is a status**: green = done, red = trouble, amber = running late — that is the entire list, and there is deliberately no blue among them because blue is the default accent. Badges are a neutral pill whose 6px dot is the only coloured part (`--badge-dot`), and `upcoming` — the state of almost every trip — sets no dot colour at all; the trip band's edge stripe is `--border-strong` except when a trip is ongoing, where it takes the accent. Both were fully tinted once and a list of ordinary trips came out a column of coloured chips, which is a lot of signal for "nothing has happened yet". Airline chips are neutral for the same reason: the carriers' liveries were nine more hues on a page whose point is that colour means status. (3) **Capitals are reserved for things that genuinely are capitals** (IATA codes, flight numbers, booking refs); status tags, section headings and field labels are sentence case. The tracked-out ALL-CAPS label was removed everywhere on purpose — bringing one back makes it read as a code
- **Accent presets** (`lib/accentStore.ts` + the `data-accent` blocks in `app.css`). Five: sky (default), ocean, dusk, orchid, graphite. Each preset needs **both** a dark block and a light block; the light selectors (`:root:not([data-theme="dark"])[data-accent="x"]`, `:root[data-theme="light"][data-accent="x"]`) outrank the dark one on specificity, so file order does not matter — but a preset missing its light block leaks its dark cut into the light theme. Green and amber are absent from the set on purpose, because a preset colliding with "done" or "running late" makes the one place colour carries meaning ambiguous. The Settings swatches paint themselves from a **separate** `data-accent-preview` attribute, so the row shows five different colours rather than five copies of the live one
- **The accent belongs to the user; the theme belongs to the device.** `users.accent` (migration 0026) is persisted through `PATCH /api/auth/me` and returned on `/api/auth/me`, exactly like `locale` — so the app looks the same on a phone and a laptop and two people sharing a browser do not overwrite each other. `themeStore` stays localStorage-only on purpose: wanting dark on a phone at night and light at a desk is about the device's surroundings. localStorage still holds the accent as a **paint cache** so a cold start does not flash the default blue while `/api/auth/me` is in flight, and `applyUserAccent` overwrites it from the server without echoing back — echoing would let a borrowed browser donate one user's colour to the next. It is called from **three** places and all three are needed: `App.svelte`'s boot check, and both branches of `LoginPage` (password-only and post-2FA), because signing in does not remount the app. The store itself is imported from **`main.ts`**, not only from Settings, which is lazy-loaded. The preset list is duplicated in three files that must agree — `ACCENTS` (accentStore.ts), `VALID_ACCENTS` (`auth/service.py`, which 422s anything else), and the stylesheet blocks; a value with no block matches no preset and leaves the page mid-cascade
- **Buttons never underline on hover, however they are marked up.** `.btn:hover` is in the `text-decoration: none` opt-out list alongside `.card-link`, `.nav-item`, `.nav-back`, `.flight-row`, `.doc-thumb`, `.rail-mark` and `.nav-action`. Plenty of controls are anchors — "Editar viagem", "Exportar para calendário", "Cancelar" on every form — and the blanket `a:hover` underline made them read as body-text links. A button already has a shape; the underline is reserved for text that is genuinely a link, which is the whole reason it exists (see the note below on why links cannot be marked by colour).
- **Links cannot be marked by colour** — `--accent-text` is a tinted cut of the accent, and on the graphite preset it *is* the body text colour. `a:hover` carries an underline instead, and the chrome links that have their own affordances (`.card-link`, `.nav-item`, `.nav-back`, `.flight-row`, `.doc-thumb`) opt back out of it
- **Type**: Barlow + Barlow Condensed, **self-hosted** in `frontend/public/fonts/` and declared in `src/fonts.css` (latin + latin-ext subsets, ~124KB total). Barlow is drawn from public-transport signage, which is the subject's own vernacular; Condensed carries page titles, airport codes and every large numeral. A CDN link was rejected because the PWA has to render offline. Mono is the **system** stack (`--font-mono`) and is used only where a ticket uses it — flight numbers, refs, IATA pairs — not as a generic small-label face
- **Navigation is one list, two surfaces** (`lib/nav.ts`): `SideRail.svelte` (fixed icon rail, ≥900px) and `TabBar.svelte` (floating dock, <900px) both render `NAV_ITEMS` and both use `isActive`, so order, labels and active-route rules cannot drift. The CSS breakpoint is what swaps them — neither component knows about the other. Both links carry a shared `.nav-item` class and both badges a shared `.nav-badge`, which is how `tests/notifications.spec.ts` addresses "the navigation" with a `:visible` filter instead of guessing the viewport. `App.svelte` puts `.with-nav` on `.app-shell` (auth pages render no navigation at all), and that class — not `body` — carries the dock's bottom padding and the rail's left offset
- **One checkbox, shared** (`components/Checkbox.svelte`), used by the packing list and the day planner. It is a drawn `<button role="checkbox">`, not a styled `<input type="checkbox">`, for two reasons: `accent-color` renders differently on every platform (the planner's native boxes were green while the packing list's drawn ones were accent-coloured — the same control looking like two), and the tick has to be painted in `--accent-on`, which `background-image` cannot reference. The tick was hardcoded `white` before the accent presets landed, which made it **invisible on graphite-in-dark**, where the fill is near-white. It stops click propagation because a planner checkbox sits inside a card whose body toggles the card open
- **Tap targets and hover-gated controls.** A control hidden behind `:hover` is not just unreachable on a touch screen — it makes the row's *rendering* depend on hover, and a touch browser then spends the first tap applying that state instead of dispatching the click. That is why every packing checkbox needed tapping twice. Any `opacity: 0` reveal must be wrapped in `@media (hover: hover)` (`.packing-delete`, `.trip-card-img-refresh`; `.rating-half` is an invisible hit area and already guarded). The reveal selector must also name **every** wrapper the control appears in — `.trip-card-img-refresh` was revealed by `.trip-card-cover:hover` alone, so on the trip page (whose cover is `.trip-detail-cover`) it sat at opacity 0 forever on a pointer device while working fine on touch, where the block does not apply.
- **The manual image refresh lives inside the trip only**, top-right of the cover. It used to be on the trip cards too and centred over the photo, which on a phone covered the part of the image you were trying to judge — and a card is too small to judge one by anyway. `ImageRefreshManager` kept its `handleError` auto-retry (one retry per card, then the fallback glyph) and lost its `refresh` method with it; `TripCard` lost the `refreshing` / `onRefreshImage` props. Separately, `Checkbox` draws at 20px but grows its hit area to the full row with a `::after` inset — stopping inside the row's gap so it never steals a tap meant for the item text, which opens the editor. `frontend/tests/packing-touch.spec.ts` covers both on an iPhone profile, and has to pin `browserName: 'chromium'` because this project installs Chromium only
- **Icons are drawn, not typed** (`components/Icon.svelte`). The nav glyphs were text characters (`✈︎ ◷ ★︎ ✉︎ ⚙︎`) that each platform's emoji font rendered at its own weight and baseline, so the set never looked like one family. They are now inline SVG strokes inheriting `currentColor`
- **Rows vs. panels vs. bands** — three shapes, deliberately not one: `.trip-card` is a horizontal luggage-tag band (photo strip, name, status panel on the stub, status-coloured edge stripe); `.trip-section` is a region of a document; `.flight-row` is a line on a departures board with **no border of its own**, separated from its neighbours by a hairline, because the legs of an itinerary belong to one another. `SegmentRow` reuses `.flight-row` so a train sits flush with the flights around it, and overrides only the connector — the drawn hairline carries an aircraft glyph, which is wrong on a train
- **`.form-row` wraps; only `.form-row > .form-field` carries the wrap basis.** The row is `flex-wrap: wrap` with `flex: 1 1 200px` on its fields, so two fields pair up above ~420px and stack below it — without the wrap a phone shrank a datetime input to about 100px, wide enough to show "yyy" of its own placeholder. The child selector is load-bearing: `.form-section` is *itself* a column flex container, so putting the basis on every `.form-field` gave a field standing alone (notes, passenger name) a 200px basis on its **height**, i.e. a textarea followed by a hand's width of empty card.
- **`app.css` declares `color-scheme` in every theme block**, not just the palette tokens. Native controls the page cannot style — the date picker panel most visibly — follow `color-scheme`, so without it an app forced to dark opens a white calendar whenever the OS is set to light. The four declarations mirror the four token blocks (`:root` dark default, the `prefers-color-scheme: light` override, and both `data-theme` forms); the print block already forced `light` and still wins inside `@media print`. Date fields also get `cursor: pointer` (their job is to open a picker) and `not-allowed` when disabled — the day cells *inside* the panel are browser chrome and cannot be given cursors from CSS
- **`App.svelte`** — SPA router, auth checks, main layout
- **`api/client.ts`** — All HTTP calls to the backend
- **`lib/authStore.ts`** — Auth state (session user)
- `components/TripTransport.svelte` — the trip page's **Transport** section: flights and ground legs in one list, grouped Outbound / Getting around / Return by `utils.splitTransport`. Both kinds normalise to a `TransportLeg` so layovers, day dividers and leg totals are computed once (`legStats`, `connectionInfo`, `dateDividerInfo` all take legs, not flights); the rows stay separate components because `FlightRow` links to `FlightDetailPage` and a ground leg has no such page — `SegmentRow` opens the inline editor instead. `components/StationInput.svelte` is the station autocomplete. `utils.toLocalInputValue` seeds the edit form: `<input type="datetime-local">` has no timezone of its own, so without it a Beijing train opened in a European browser shows the wrong hour and silently moves on save
- `components/PlaceInput.svelte` (was `StationInput`) is the one type-ahead behind both the station and the stay pickers, switched by its `kind` prop. Two things there are not cosmetic: results are **sorted venues-before-addresses** so the "Addresses" divider renders once rather than once per run (Photon interleaves the two by relevance, which produced four headings in a six-result list), and picking a result hands back the geocoder's `country_code` and street address alongside the name — typing clears all three, because the name no longer refers to that place
- Two things on the trip page's compact cards are load-bearing and were both bugs first. `.section-note` (the empty-section sentence) is a **direct child of the section header**, ordered last with `flex-basis: 100%`, so the title and the Add button keep the first line and the sentence runs the card's full width underneath — it must never be given `text-overflow: ellipsis`, because it is a sentence explaining what the section is for and both locales' strings are far too long to seat beside a title. And `.rating-header-actions` **wraps**: below 640px each star grows to 2.75rem for touch, so five stars plus "Limpar avaliação" are wider than a phone's content column and pushed the whole document sideways. `tests/trip-detail.spec.ts` asserts both — no clipped note, and `scrollWidth <= clientWidth` at 390px with a rating set.
- `components/TripExpenses.svelte` sizes its rows with a **container query** (`container-type: inline-size` on `.expenses-list` and on `.expense-add-form`), not a viewport media query. The same list renders at ~380px in the trip page's aside column and at full width below 1000px, so a viewport query still thinks it is on a desktop exactly where the row is narrowest. Under 480px of *container* the description takes the whole first line and currency/amount/buttons drop to a second — sharing line one with the buttons wrapped a four-word expense into three ragged lines. `.expense-desc` deliberately **wraps rather than truncating**: the amount and the buttons are fixed-width, so the description was the only thing that gave, and "Airport c…" is a row that says nothing about where the money went.
- `components/TripStays.svelte` — the trip page's **Stays** section, sitting between Transport and the day planner (how you move → where you sleep → what you do each day). `components/StayRow.svelte` is deliberately *not* built on `.flight-row`: giving a stay the same row shape as a leg made the two read as interchangeable. The uncovered-nights line and the "outside the trip's transport" warning are computed client-side by `utils.accommodationGaps` / `utils.stayOutsideTravel` — both are advisory, and no backend endpoint exists for either. `stayOutsideTravel` returns three states, not two: `before` / `after` for a stay with no overlap at all, and `overruns` for one that overlaps but whose check-out runs past the last arrival. The `overruns` state stays advisory even though the form now *blocks* the same condition on save: the form measures against the last flight/segment arrival, deliberately **not** against `trip.end_date`, which is derived *from* the stays — validating against that would mean a stay could never be extended, since the row being edited is itself what sets the ceiling. The warning is what catches a row that drifted out of range afterwards (a leg deleted, a flight rescheduled) or was written before the block existed. The asymmetry is deliberate: an overrunning check-out is flagged, an early check-in is not, because the night before an early departure is the standard airport-hotel booking and warning on it would fire on ordinary trips
- `components/TripDayCard.svelte` bands stays using **two different keys on the same card**, which is easy to collapse into one by mistake: a stay is *banded onto a day* by comparing local calendar dates (`utils.staysForDay`, over the backend's `check_in_date`/`check_out_date`), while its check-in and check-out *rows* sort on the real instant alongside flights and ground legs. Note also that a stay covers the night of every date from check-in up to but **excluding** check-out — the check-out day gets an entry without counting as a night
- `pages/AddTransportPage.svelte` — the single entry point for adding a leg, at `/trips/:tripId/add-transport`. The type picker (flight / train / bus / ferry / car) decides **which API the form calls**: `flightsApi.create` writes a `flights` row, everything else `segmentsApi.create` writes a `trip_segments` row. It is deliberately *only* the entry point that is shared — merging the tables was rejected in migration 0023 and that reasoning still holds; what was wrong was the UI asking you to decide "flight or ground transport?" before you had described the leg. Choosing the type also swaps the place inputs (`AirportCombobox` for IATA vs `PlaceInput` for OSM stations), which is the part a field-hiding implementation would miss. The service section is titled with the **chosen type** (`segments.type_*`), not with the flight heading it started out reusing — a ferry announcing itself as a *voo* was the first thing anyone noticed. Note that several `add_flight.*` keys (`section_departure`, `section_arrival`, `seat`, `booking_ref`, `cancel`, `saving`) are reused verbatim in ground mode: their *names* are historical, their text is mode-neutral. The **seat field is dropped for `car`** — you are the one driving — in both this form and `TripTransport`'s inline editor, and the payload sends `seat: null` for a car rather than whatever was typed before the switch, so a stale "Vagão 3, 12A" cannot ride along on a drive. Operator and booking reference stay, because a rental has both. Times, seat and booking reference are **shared state across the switch** — realising a leg is a train after typing its times should not cost the times. **Every field is visible** — no disclosure — and the required ones carry a red `*` (`.req`, `--danger-text`). Red is otherwise reserved for trouble in this design language; a required marker is the one convention readers already know, and marking the optional majority instead would be more ink for less signal. The only entry points are the Transport section's own button and the whole-trip empty state — the trip header's copy was removed, because a second door to the same room is what made the two-button split feel arbitrary in the first place. Adding is unified; **editing is still split** (a flight has `EditFlightPage`, a ground leg has the inline editor in `TripTransport`) — that asymmetry is known and deliberate, since a flight has a detail page to hang an editor off and a ground leg does not
- `pages/EditFlightPage.svelte` — full-page flight editor, reached from the owner-only **Edit Flight** button on `FlightDetailPage` (a ground leg's inline editor has no flight equivalent because a flight has a detail page to hang it off). It resubmits **every** field on save, which is why the backend's `update_flight` re-runs `apply_airport_timezones` and recomputes duration/status: the two datetimes go out as naive local time at each airport (seeded by `utils.toLocalInputValue`, the same helper `TripTransport` uses), never as the stored UTC. The route exists under both `/trips/…` and `/history/…` and derives which from `$location`, like `FlightDetailPage`
- `components/TripMap.svelte` — the **Move map / Lock map** toggle exists because `dragging` starts off on touch devices (a full-width map answering vertical swipes traps the page scroll) and there was otherwise no way to turn it back on; the button flips `map.dragging` imperatively, and the map's creation effect reads that state through `untrack` so flipping it doesn't tear the map down and rebuild it. Wheel zoom stays off in both states — it has no gesture of its own to trap and would just steal the page's scroll; zooming is the +/- control and pinch. Touch detection is done locally (`ontouchstart` / `maxTouchPoints`) rather than via `L.Browser.touch`, which is only readable after Leaflet's dynamic import has resolved — too late to create the map in the right state.
- **The API cache is not scoped to a user, so it is purged whenever the account changes** (`lib/apiCache.ts`, called from both `LoginPage` branches and `TopNav`'s sign-out). `sw.js` caches `GET /api/*` under one cache per install and a PWA install is shared by everyone who signs in on that device; left in place across a sign-in, stale-while-revalidate hands the next user the previous one's trips and stats instantly while the network copy is still in flight. One account was reported showing **another's visited countries** — recomputing both users' stats against the real database confirmed the backend was correctly scoped (`f.user_id` / `t.user_id`) and the account in question had no flights at all, so what it displayed was cache. Purging on *both* sides is deliberate: either can be the transition that happens on a shared phone. The page reaches CacheStorage directly rather than messaging the worker, so it works with no worker controlling the page. Static caches are left alone — the shell is the same for everyone, and dropping it would cost a cold start for no privacy gained.
- **`sw.js` purges the API cache `await`-ed inside the mutation's own response**, not in `event.waitUntil`. `waitUntil` only keeps the worker alive; it promises nothing about finishing before the next fetch, so the re-read a page issues straight after a mutation could win the race and be served the pre-mutation copy by stale-while-revalidate. That is what made a saved budget show the old figure on a phone until you navigated away and back. Awaiting costs one local CacheStorage sweep on the write path and buys a real ordering guarantee: by the time the page sees the write resolve, there is nothing stale left to serve it. A **failed** mutation leaves the cache alone — nothing changed on the server, so dropping it would only cost a round trip. `src/lib/sw.test.ts` drives the worker's `fetch` listener against a stubbed `self`/`caches` and asserts the purge lands before the response; it fails against the `waitUntil` version.
- `components/TripMap.svelte`'s OSM fallback is for a CARTO that is *unreachable* (adblocker, DNS filter), and demotes only after `UNREACHABLE_TILE_FAILURES` errors **with no tile having loaded** — a layer that drew even one tile is reachable and is never demoted. Switching on the first `tileerror` meant one dropped request on a phone swapped the basemap for OSM, whose labels are in the local language (上海) where CARTO Voyager's are Latin (SHANGHAI), so a working map "turned Chinese" on mobile while a desktop that never dropped a tile stayed correct. `sw.js` was the other half: its catch-all `networkFirst` matched on pathname alone and so answered dropped *cross-origin* tile requests with a JSON 503, manufacturing the hard error — it now returns early for anything not same-origin
- `components/TripMap.svelte` reads `carto_api_key` off `$currentUser` (see the `/api/auth/me` note below) and **only adds the CARTO layer when it is set** — unkeyed Voyager tiles come back as a normal 200 carrying an "API KEY REQUIRED" watermark, so the `tileerror` → OSM fallback never fires on them; keyless installs go straight to OSM instead
- `components/TopNav.svelte` is the page header on every page and takes an optional **`actions` snippet**, which is where a page's primary control belongs (TripsListPage puts "New trip" there). It imports `t` from **`../lib/i18n`**, not from `svelte-i18n` directly: several page tests mock `../lib/i18n` and never initialise a locale, so a bare `svelte-i18n` `$t` call in the header throws "Cannot format a message without first setting the initial locale" and fails every test that renders a page
- `components/TripCard.svelte` splits its stub into `.trip-card-main` (everything you read) and `.trip-card-aside` (where the trip stands — the badge snippet and the footer snippet), side by side from 700px and stacked below it. The badge was moved out of the title row so a long trip name is never squeezed. The card's version is deliberately coarser: it has only per-kind *counts* from the list DTO, so a mixed trip there says "3 legs", while the page has the rows loaded and can name each kind. Zero-count kinds are omitted and an empty trip renders nothing, because a row of noughts is not a summary. The glyph order is fixed (`SEGMENT_ORDER`) and an unrecognised kind gets a neutral `↔`, the same two rules the card's chip follows. Per-currency **expense totals** follow, through `utils.formatCurrencyTotals` — also shared with the card, which had its own copy of the same rounding. The header seeds them from the trip payload and then takes them live from `TripExpenses`' new `onchange`, which is **gated on `!loading && !loadError`**: the effect runs once on mount with an empty list, and `{}` is not nullish, so an ungated report replaced the seeded total with nothing at all.

Two independent flows cannot open that hole; `grid-auto-flow: dense` does not help, since it only backfills spanning items. Below 1000px the wrappers are plain blocks and the DOM order is unchanged, so mobile reads exactly as before. Documents rides at the **foot of the spine** rather than in the aside: it is the least-used card on the page, so it wants to be low, but stacking it with the notes and the rating left one column holding three things nobody opens while the other held everything anyone came for. At the spine's foot it is low *and* the two columns end at roughly the same depth. **Below the breakpoint the two wrappers go `display: contents`** and the page becomes a flex column, so the sections can be sequenced independently of the column they belong to: `.trip-section-documents` takes `order: 1` and `.trip-section-tail` (notes, rating) takes `order: 2`, which puts Documents directly above the notes on a phone instead of between the day planner and the packing list. Print forces it back to one column. `pages/SettingsPage.svelte` carries `settings-page`, which caps the column at 820px — a form is read one field at a time and a 1000px-wide text input is harder to scan, not easier

## Features

### Trip & flight management
- Auto-groups flights into trips by booking reference, then 48h time proximity
- Trip cards count flights, ground legs and stays **separately** (`TripCard.contents`), because a rail trip reading "✈ 0 flights" is true and useless. `segment_types` on the list DTO lets a single-kind trip say "2 trains" while a mixed one falls back to the generic "2 legs" — no single icon honestly represents train-plus-ferry, and the **icon must keep that same promise**: it used to default to the train glyph whenever the types were mixed or unrecognised, so a ferry and two drives read "🚆 3 legs", claiming a train the trip never took. A mixed trip now shows one glyph per kind it actually contains, in the fixed `SEGMENT_ORDER` so the chip does not reshuffle between renders, and an unmappable kind gets a neutral `↔` rather than a guess. `TripRepository.get_segment_counts` / `get_stay_counts` are bulk siblings of `get_flight_counts`, attached in `TripService._attach_extras`
- **One "Add transport" entry point** covers flights and ground legs alike — a type picker (flight / train / bus / ferry / car) chooses which fields show and which API the submit hits. Create/edit trips and flights manually; delete (owner only). Editing a flight covers every field (route, times, terminals, gates, seat, cabin, booking ref, passenger, notes); times are typed as local time at each airport and re-localised to UTC on save, which also recomputes duration/status and the trip's span
- **Trash and activity log** (Settings): a deleted trip or flight is kept with everything that was on it and can be restored or deleted permanently; deletions, restores, permanent deletes, merges, full syncs and parser rescans are listed with a date (plus regroups, from before that button was removed). A deleted booking can be imported again from the same mail
- Export trips as iCalendar (.ics) files — `trips/ical_service.py` emits flights and `trip_segments` as timed VEVENTs (both with a `-PT1H` VALARM) and each non-empty day-planner day as an **all-day** VEVENT. **Timed events are floating local times** (no `Z`, no `TZID`) whenever the place's timezone is known — each end of a flight in its own airport's zone, a ground leg in each station's, a check-out in the property's — because an itinerary should read the way its tickets do rather than rebased on whatever zone the reader's phone is in (a 14:00 Lisbon departure showed as 10:00 in São Paulo). An event whose zone is unknown stays UTC: printing some other zone's clock as if it were local is a wrong time presented as a right one. `_plus_minutes` therefore parses **both** stamp forms — parsing only the `...Z` one would silently return a floating stamp unchanged and reintroduce the zero-length check-out event it exists to prevent. Three further details are load-bearing: all-day `DTEND` is *exclusive* (next day, or clients render a zero-length event and hide it); TEXT values go through `_escape` because an unescaped comma or semicolon splits a field into a value list, which free-text notes produce constantly; and lines are folded to 75 octets by `_fold`, which backs off on `encoded[end]` rather than `encoded[end - 1]` — the latter stops on a lead byte and eats the character, mangling CJK station names
- Notes per flight (up to 10,000 chars); calendar-style day notes per trip
- Trip rating (0.5–5 stars in 0.5 increments)
- **Trip expenses**: add itemised expenses per trip (description, amount, currency); totals grouped by currency shown in trip detail and trip cards; 41 supported currencies; per-user default currency (set in Settings)
- **Expense splitting**: each expense records who paid (`paid_by`: a collaborator or a guest, defaults to the creator) and who it's split equally between (`participants`, defaults to everyone currently on the trip); expense rows show who added them; `GET /api/trips/{trip_id}/expenses/balances` returns each participant's net balance per currency (what they paid minus their share)
- **The payer picker does not offer you twice.** `list_participants_for_trip` always includes the trip owner and every accepted collaborator, so the caller is already in it; the add form used to prepend a `""` option labelled "Me" on top of that, making picking yourself two identically-meant choices (the edit form never had one). The option now renders **only when the list is empty** — the genuine fallback, where the payer is omitted and the backend defaults to the creator — and `openAddForm` preselects your own row by key. `displayName` marks that row `expenses.you` (`{name} (you)`) in both payer selects and both split-between lists rather than renaming it, since the name is what the rest of the trip calls you
- **Guests**: non-account trip companions for splitting expenses with people who don't have a Partiu account (`POST /api/guests` creates one, owned by the caller; `GET /api/guests` lists the caller's own; `PATCH /api/guests/{id}` renames one; `DELETE /api/guests/{id}` — blocked while referenced by an existing expense); a guest can't be deleted while referenced by an existing expense; guests are scoped per trip — `GET /api/trips/{trip_id}/expenses/participants` (the payer/split-between picker) only surfaces trip collaborators plus guests already tagged on *that* trip, not every guest the caller has ever created, so a guest added on one trip doesn't leak into an unrelated trip's picker; paid_by/participants validation on create/update additionally accepts a guest the caller owns but hasn't tagged on this trip yet, so a freshly quick-added guest can be used immediately as that first expense's payer/participant; a Settings section (add/rename/delete) manages the caller's own guest address book directly, independent of any single trip

### People on a trip
- A **People** section on the trip page lists its owner, accepted collaborators, outstanding invitations and its guests, and is where guests are added to or removed from *this* trip
- Guests are scoped per trip by a real roster (`trip_guests`): adding Jimmy, Lucas and Vivian to one trip makes exactly those three the people its expenses can be paid by and split between, while a trip nobody was added to offers only you and its collaborators
- A guest can be created and put on the trip in one step, or picked from the ones you have travelled with before; removing one is refused while an expense on that trip still names them
- **Companion counts on the trip card and in the trip header** (`utils.tripPeople`): `👥 4 people` counts the owner, accepted collaborators and roster guests, with outstanding invitations kept as a separate `✉ 1 invite pending` chip — an invitation is not a companion until it is accepted. A solo trip prints nothing at all, the same rule the contents line follows. The counts ride on the trip payload rather than `GET /api/trips/{id}/shares`, which is owner-only — a collaborator deriving them from there would be told they are travelling alone

### Trip budget
- A spending limit per trip (`trip_budgets`, migration 0030), keyed on **(trip_id, user_id)**: a budget belongs to a person, not a trip, so two collaborators on one trip each keep their own
- **A budget can name more than one person** (`trip_budget_members`, migration 0031), and then belongs to all of them. Two people travelling on one purse split every bill between themselves, so two separate budgets filled in lockstep at half speed and told them nothing — the shared one counts their **combined** share. Members are `(type, id)` like expense participants, so a companion with no account is a **guest**, which is the whole reason guests exist. The **owner is stored as a member row** rather than implied, so `share_by_trip`'s SQL is one uniform join instead of a join plus a special case
- **Resolution is own-first, then named**: `BudgetRepository.resolve` returns the caller's own budget if they have one, otherwise one whose member list includes them. Own wins because setting a budget is deliberate and being added to someone's is not. That fallback is what lets both halves of a couple open the trip and read the same bar. The consequence is that **a member editing a shared budget edits that one**, not a private copy beside it — otherwise "we share a budget" would quietly become two budgets the moment the other person adjusted it — and `clear_budget` clears it for everyone. Leaving is unchecking yourself from the member list; the save after that is your own again. `set_budget` keeps the owner in the list unconditionally, so a budget can never end up belonging to nobody
- **`members=None` leaves an existing member list alone** and starts a new budget as the caller's own, so a client that predates sharing cannot silently un-share a budget by saving an amount
- **Spend is the members' combined share**, not what they paid out: an expense split four ways counts a quarter to a solo budget and a half to one shared by two of those four, whoever paid. What you paid is a cash-flow question and `get_balances` already answers it — a budget is what the trip costs the people it belongs to. `_share_by_currency` therefore skips expenses no member is tagged in **even when one of them paid for it** (you are settling up for other people, not spending on yourself), and skips participant-less expenses rather than dividing by zero. `_member_refs` resolves names against the trip's participant list, so a member who has since left the trip is dropped rather than printed as a bare id
- **Only the budget's currency counts.** Spend in any other currency comes back in `uncounted` and is listed beside the bar, never converted — there are no exchange rates in this app, and a converted figure would be a guess presented as a fact, the same thing `parsers/validation.py` refuses on the other side of the codebase. With no budget set, every currency lands in `uncounted`, so the UI can offer to set one against a number the traveller already recognises
- **The bar is a traffic light that also dims and brightens**: green while there is room, amber from 80%, red **at** 100% (`WARN_AT` in `TripBudget.svelte`) — at, not past: spending exactly your budget is spending all of it, and a bar still amber while the money is gone reads as "nearly there". Exactly at the limit the note says the budget is spent rather than "0 over budget" — and within each band it **pales in and deepens** as the bar fills, so you can see where in the band you are, not only which band. The band picks the hue; `--budget-mix` (35–100%) picks its strength, applied with `color-mix(… , var(--bg-subtle))` so "pale" means *less of the colour* and reads correctly in dark mode as dimmer rather than lighter. `background` is declared twice on the fill: the flat colour is what a browser without `color-mix` keeps, degrading to exactly the three-step bar this replaced. The over-budget band tops out at +30% — past that a deeper red says nothing the number has not. The floor of 35% exists because a bar mixed all the way into its own track is invisible. Amber lands *before* the limit because that is when the number is worth knowing. This is the **one place green appears outside its "done" meaning**, and it works because the three colours here are one scale rather than three statuses — a badge is green or it is not, whereas this bar passes through green on its way to red. Do not take it as licence to tint anything else green. The bar stops at 100% while the figure keeps going — an overflowing bar says nothing the colour has not
- The trip **header** prints the budget as its own chip (`🎯 EUR 255 / EUR 800`), coloured by the same state as the bar. It is deliberately *not* folded into the expense totals beside it: those are the **trip's** spend per currency, this is the budget members' share against **their** limit, and adding the two together would be a lie. `budgetIsShared` swaps both the chip's tooltip and the sentence under the panel to `budget.hint_shared` — a bar measuring two people's spending explained as "your share" is a wrong caption on a right number. The figure is reported upward by `TripBudget`'s `onchange` rather than fetched a second time, and the thresholds live in `utils.budgetLevel` / `BUDGET_WARN_AT` so the panel and the chip cannot drift apart.
- **The trips list shows the budget only when it needs attention** — amber or red, never a figure for a budget with room left. A card is a glance, and an overview exists to surface the one trip worth opening; the bar and the numbers live on the page you opened deliberately. Same reasoning as the status badge, which shows no dot for `upcoming`. There is deliberately **no check on whether the trip has started**: a trip weeks away has already bought its flights and booked its hotels, and that money is spent.
- **The list's budgets are two bulk reads, not one per card** (`ExpenseService.budgets_for_trips` → `BudgetRepository.resolve_for_trips` + `share_by_trip`). The share SQL must keep matching `_share_by_currency`'s Python: join each expense's participant rows to the budget's **member** rows and divide by the participant count — an expense no member is tagged in never joins, so paying for other people still counts nothing, and two members tagged in one expense contribute two shares. `share_by_trip` takes **(trip_id, owner_user_id) pairs**, not a single user, because the budget applying on each trip may belong to a different person; `resolve_for_trips` expresses own-before-shared as `ORDER BY is_own DESC` plus a first-wins loop rather than two queries. `test_budget.py::TestBulkBudgetsForTheTripsList::test_matches_the_single_trip_answer` and `TestSharedBudgetsInBulk::test_bulk_matches_the_single_trip_answer_for_a_shared_budget` assert the two agree.
- **`TripBudget.reload()` is a method, not a `revision` prop.** Bumping a counter from `TripExpenses`' `onchange` re-renders the trip page, which hands the list a fresh callback, which re-runs its reporting effect, which bumps the counter again; every trip-page test timed out on that loop before it became a call through `bind:this`
- **`TripBudget`'s member picker is the expense participant list**, fetched lazily when the edit form first opens — most visits only read the bar. The row is hidden entirely when the trip has one person on it (a question with one answer), and a failed fetch leaves it empty rather than blocking the form.
- **`components/PeoplePicker.svelte` is the one "pick some of the people on this trip" control**, used by the budget's share-with row and by *both* expense split-between forms (add and edit). It was three hand-rolled copies of the same wrapping pill row; they had already drifted (one painted its tick `white`, one did not) which is why this is a component and not a shared stylesheet class. It is **controlled**: the parent owns the selected-key `Set` and the picker only reports `onToggle`, so nothing here can desync from the form that submits.
- **The picker's list is bounded by the trip, not the instance** — `list_participants_for_trip` returns the owner, *accepted collaborators on that trip*, and guests *already tagged on that trip*. A thousand accounts on the server add no rows, and the caller's wider guest address book is deliberately not surfaced (`guests_service.list_for_trip`). Twenty guests on one group trip is reachable, though, and that is what the two defences are sized for.
- **It is a token combobox, not an inline list**, and that is the third shape this control has had — the first two (a wrapping pill row, then a capped scrolling list) both cost the form a fixed block of height on *every* trip in order to serve the rare crowded one. Here the resting size is what you have **chosen** (usually one or two tokens), the candidates live in an absolutely-positioned overlay, and an eight-person trip costs the form exactly as much as a two-person one.
- **Focus opens the full list**, deliberately. A pure type-to-search box hides the fact that there is anything to pick at all; this is the same reason `PlaceInput` reopens its results on focus. Removing it would make the control undiscoverable for someone who does not already know who is on the trip.
- **Suggestions exclude what is already chosen** — a picked person is a token, and leaving them in the list too offers one person in two places, which is exactly the bug the payer select had.
- **The search folds accents** (`fold`, mirroring `utils/text.py::fold_text`) so `joao` finds `João`. The names here are typed by hand in a pt-BR app; a search that cannot find its own users' names is worse than no search.
- Keyboard follows `PlaceInput`: arrows walk, `Enter` picks the highlighted row **or** the only match, `Escape` closes, and `Backspace` on an empty box takes back the last token. `Enter` on an ambiguous query picks nobody and does not submit the surrounding form — `PeoplePicker.test.ts` pins that case specifically. Unlike `PlaceInput` there is **no debounce and no request sequencing**: the candidates are already in memory, so filtering is synchronous.
- The query **clears after each pick** and the list stays open, because adding two people in a row is the common case and a box that closed would make the second one a fresh hunt.
- Tokens are a **neutral pill, not accent-filled** — the accent is worn by four things in this design language and a list of companions is not one of them.
- **`TripExpenses` still owns `checkboxIcon`** for its balances-combine list, and its tick must stay on `--accent-on`: it hardcoded `white` long after `Checkbox.svelte` was fixed, which made it invisible on graphite-in-dark where the accent fill is near-white — the fourth instance of the bug the accent notes above warn about. Note `.balance-row` there is a genuine toggle button and correctly keeps `aria-pressed`; don't sweep it into a rename.
- The overlay's geometry **cannot be asserted in a Vitest component test**: happy-dom does not apply Svelte's scoped `<style>` blocks, so `getComputedStyle` reports nothing for them. Those tests cover behaviour (filtering, keyboard, tokens); that opening the dropdown does not grow the form was verified in Chromium against a throwaway harness, and would need a mounted-component Playwright setup to keep permanently. `companions` (everyone but you) is printed **beside the bar**, not behind the form: one extra name is the whole difference between "my budget" and "our budget", which changes what the figure above it means.
- `lib/currencies.ts` holds the picker's currency list, shared by the expense and budget forms and mirroring `SUPPORTED_CURRENCIES` in `backend/expenses/domain.py` — a code offered by the form but refused by the API is a save that fails for no reason the form can explain

### Ground transport (train, bus, ferry, car)
- Manually-added non-flight legs on a trip (`POST /api/trips/{trip_id}/segments`) — no email parsing, by design; added through the shared **Add transport** page rather than a button of their own
- Station type-ahead via Photon/OpenStreetMap (`GET /api/stations/search`), returning real station coordinates and the country code that makes the leg count toward visited countries
- Local times at each station are converted to UTC using the timezone derived from those coordinates, so cross-timezone durations are real elapsed time
- Ground legs render on `TripMap` as dashed straight lines colour-coded per type, distinct from the great-circle flight arcs, and appear in the **day planner** interleaved with that day's flights in time order (`TripDayCard` sorts on the real instant, not the printed local time, since a day's two ends can sit in different zones)
- `TripRepository._recompute_span` unions flights **and** `trip_segments` for the trip's start/end dates — the planner renders one card per day in that range, so a day holding only a train had no card to appear in until segments counted. Origin/destination stay flight-only (they are IATA codes; a station has none). The MIN/MAX there are the *aggregate* forms: the two-argument scalars return NULL when either side is empty, which would blank the span of a flights-only or segments-only trip. `SegmentService` calls `recompute_span` after every mutation
- The geocoder is optional (`PHOTON_URL`): a hand-typed place saves fine, it just gets no map line and no timezone conversion
- **Countries, leg counts and nights count in Stats; distance never does.** `stats/repository.py::list_ground_countries` unions `trip_segments` and `trip_stays` into the visited-countries set; `count_ground_legs` and `list_stay_night_ranges` add the two exact-count cards. There is no 24h-layover rule for ground legs, unlike flights: that rule exists because airside transit is not visiting, and changing trains puts you in the city past no border fiction. There is deliberately **no ground distance** — rail track runs well above the great-circle line (Stockholm-Oslo ~520 km straight against ~600 km of track), so an estimate rendered as a statistic would be the guess this codebase refuses elsewhere. `_count_distinct_nights` unions dates rather than summing each stay's nights, so two overlapping bookings are still one night away

### Car rental
- A hired vehicle on a trip (`trip_car_rentals`, migration 0032): company, vehicle, two counters, two instants, booking reference and driver. Its own section on the trip page between Stays and the day planner
- **Not a `segments.car` row.** That is a *drive*; this is a contract over days. They coexist — the rental says what was hired, a `car` segment says where it was taken — and a trip can hold both. See the `car_rentals/` note above for what forcing one into the other would cost
- Two places rather than one, because one-way hires are ordinary; each end keeps its own timezone and its own local calendar date
- **Imported from Hertz, Sixt and Europcar confirmations** (`parsers/car_rental.py` → `sync/car_rentals_import.py`), all three of which sit on the blocked-sender list and are read ahead of it. The booking joins the trip whose flights *or stays* it spans, or opens one
- Day planner bands the car across every day it is held — **including the drop-off day**, unlike a stay, whose check-out day is not a night: you still have the car the morning you return it (`utils.rentalsForDay`)
- iCalendar export gives **both** counter appointments a `-PT1H` alarm — unlike a stay, where only check-out gets one, because a collection time is binding at most vendors and a late return is charged. The all-day band is suppressed on a same-day hire, where the two timed events already say everything
- Countries count in Stats from **both** ends; the trips list and the trip header count rentals apart from ground legs, since folding a hire into the leg count would claim a drive that may never have happened

### Stays (hotels, Airbnbs, hostels)
- Manually-added accommodation on a trip (`POST /api/trips/{trip_id}/stays`); a hand-typed place saves without coordinates
- **Imported automatically from schema.org booking markup** (`parsers/schema_org.py` → `sync/stays_import.py`): property, address, ISO country, check-in/check-out, booking reference and host phone, read from the typed block rather than the layout. Platform-agnostic by design — Airbnb is what it was measured against, and Booking.com / Hotels.com / Trip.com are covered the moment they emit the markup. The import runs **ahead of the blocked-sender skip**; the country code comes from the platform rather than a reverse-geocode, and the address is geocoded through Photon only for the coordinates (the markup carries none, and none of the six measured bookings had a static map URL to scrape one from)
- Accommodation + address type-ahead (`GET /api/places/search`, in `stays/routes.py` because a stay is its only caller). `photon.search_places` runs the tagged accommodation query first and only falls back to a **second, untagged** address query when that came back thin — hotels are in OSM and searchable by name, a private rental usually is not, so typing a hotel name still costs one request while typing a street gets the address results it needs
- Own section on the trip page between Transport and the day planner; records name, address, kind, check-in/out, room type, guests, booking reference, confirmation and contact
- The add form seeds **14:00 check-in / 11:00 check-out** (`DEFAULT_CHECK_IN` / `DEFAULT_CHECK_OUT` in `TripStays.svelte`) on the trip's first day and its **last transport** day. Check-out is seeded off the transport rather than `trip.end_date` for the same reason the after-travel block measures against transport: `end_date` counts other stays, so seeding from it can open a fresh form already showing an error. Both times are conventions, not standards — properties vary — and stay editable
- Local times at the property are converted to UTC via `airports.timezone.get_timezone_for_coords`, and the **local calendar dates** are stored alongside — see the `stays/` entry above for why they are not derived on read
- Day planner shows "night 2 of 4" in each covered day's header and interleaves check-in / check-out into that day's time-ordered entries
- `TripRepository._recompute_span` unions flights, `trip_segments` **and** `trip_stays` (the latter via its local-date columns), so stays extend the trip rather than being constrained by it
- Uncovered nights and stays that do not overlap the trip's transport are surfaced as non-blocking UI warnings, never as rejected saves
- iCalendar export emits an all-day block per stay with `DTEND` = check-out **+ 1 day** (DTEND is exclusive; without the extra day the block stops before the checkout morning), plus a separate timed check-out event carrying the `-PT1H` alarm — an alarm on an all-day event fires at midnight in whatever zone the client picks. `LOCATION` prefers the street address and `GEO` is emitted only when real coordinates exist
- **Countries count in Stats; nothing else does** — see the ground-transport note above; `list_ground_countries` covers stays on the same terms

### Place country codes (visited countries beyond flights)
- `trip_segments.departure_country` / `.arrival_country` and `trip_stays.country` hold ISO-3166-1 alpha-2, **recorded from the geocoder result the user picked** and never inferred from the stored coordinates
- That rule came from a measurement, and reversing it will reintroduce a real bug: picking the nearest airport out of the local `airports` table (which has `country_code`) was tried first and put **Malmö Central in Denmark**, because Copenhagen's airport is closer to it than any Swedish one. Border cities are exactly where a rail trip crosses a frontier, so that is the worst place to be wrong — and a wrong country rendered as a visited fact is worse than a missing one. `photon.reverse_country` gets Malmö right
- Rows written before migration 0025 are backfilled by `stays/country_backfill.py`, started on a daemon thread from `main.py`. It resolves through Photon's `/reverse`, is bounded per run, and only sets its `place_country_backfill_done` flag on a sweep that left nothing behind — a partial run (cap hit, or geocoder down mid-way) retries next start, the same discipline `backfill_rank_columns` uses. With no geocoder configured it does not run and does not set the flag
- A place with no coordinates (hand-typed, geocoder unreachable) has no country and contributes nothing — by design
- `StatsPage.svelte`'s empty state keys off `total_flights === 0 && unique_countries === 0`, not the flight count alone; a rail-only account has real countries and no flights

### Email sync & parsing
- IMAP sync (Gmail App Password or custom IMAP host/port) per user
- Built-in airline rules — 19 supported: LATAM (LA), SAS (SK), Norwegian (DY), Azul (AD), Lufthansa (LH), British Airways (BA), ITA Airways (AZ), Kiwi.com, Ryanair (FR), Austrian Airlines (OS), TAP Air Portugal (TP), Finnair (AY), Wizz Air (W6), Brussels Airlines (SN), Iberia (IB), Vueling (VY), Qatar Airways (QR), Turkish Airlines (TK), Pegasus Airlines (PC); `PARSER_VERSION = '34'`
- **Structural extraction only** — no generic proximity-guessing tier; see the `parsers/validation.py` entry above for why it was removed and what replaced it
- **Accommodation from schema.org markup**, any sender: a typed `LodgingReservation` becomes a stay on the trip its flights belong to, or on a new trip when there are none. Read-only on cancellations — no platform in the measured corpus sends a parseable one
- Localised forwarded-message headers (`De:`, `Von:`, `Från:`, …) so forwarded itineraries still reach their airline rule
- Cancelled legs are recognised and skipped: Lufthansa schedule-change mails reprint the dropped leg (`Estatuto: Cancelada`), and Finnair's cancellation notice reprints the whole itinerary in the confirmation layout
- **Airline-independent GDS e-ticket parser** (`parsers/gds_eticket.py`): reads the shared Amadeus/Sabre/Travelport ticket-receipt (ITR / ITR-EMD) layouts — HTML table, compact one-line-per-leg, and the fixed-column plain text — for any issuing airline, including per-leg terminals; prefers the bare IATA pairs the receipt restates in its baggage blocks over city-name resolution
- **Turkish Airlines** (`parsers/airlines/turkish.py`) reads TK's own branded "Ticket Details" mail — *not* a GDS receipt, so `gds_eticket` finds no marker in it — in both renderings: the HTML leg blocks and, as a fallback, the `TicketDetails.pdf` detail blocks. Neither rendering repeats the date inside a leg block, so both resolve it from the nearest line above that is a bare date or a route header (`Istanbul (IST) - Denizli (DNZ)`); "nearest line that parses as a date" would reach the `Transaction date:` line at the top and file every leg on the issue date. Passenger and booking reference are read from TK's own labels because this layout defeats the shared extractors — its "Passenger name" heading is followed by a route, and the PDF prints the greeting between "Reservation code" and the code. Turkish month names live in `engine.MONTH_MAP`
- **Pegasus Airlines** (`parsers/airlines/pegasus.py`) reads PC's Turkish-language "Rezervasyonun onaylandı!" confirmation. There is no attachment behind it, so the HTML leg block is the only rendering. The block is walked line by line rather than matched by one regex: the duration line and both terminal lines are independently optional, and a regex with three optional filler lines drifts onto the next leg's values as soon as one is missing. The date is never inside the block, so it comes from the nearest *bare-date* line above — "nearest line containing a date" would reach `Check-in Açılış: 12 Eylül 2026 02:45` at the top of the mail and file the outbound leg on the check-in opening day. The anchor is pinned to `PC` rather than `[A-Z]{2}` so no other carrier's number starts a block, and the passenger comes from PC's own greeting ("Sevgili …"), which the shared extractor does not recognise
- **Schedule changes applied to stored flights** (migration 0034 → `pipeline._record_reschedule` / `_apply_schedule_change_notices`): a reprinted itinerary with new times keeps the previous times on the leg and notifies; a leg moved to another day lands on the same row instead of beside it (`find_moved_leg`: number + route + booking reference within ±3 days); an itinerary-less notice (SAS) flags the booking's legs and points the traveller at the airline. Amber "Rescheduled" badge and a previous-times banner in the UI
- **Cancellations applied to stored flights** (`parsers/cancellations.py` → `pipeline._apply_cancellations`): SAS, Lufthansa and Finnair cancel a *booking* and are read by reference; Austrian cancels a *leg* and is read by flight number and date. Marked `status = 'cancelled'`, never deleted; excluded from Stats; a schedule-change mail is deliberately not read as one; a cancellation older than the flight it names is ignored
- **Car rental confirmations** (`parsers/car_rental.py`): Hertz, Sixt and Europcar, read from each vendor's own plain-text layout
- **Plausibility gate** (`parsers/validation.py`): drops legs that are physically impossible (great-circle distance vs. elapsed time, arrival before departure, same origin and destination) rather than storing them, reports broken leg chains, and rolls year-less dates forward when an itinerary would otherwise travel backwards across New Year
- **Ranked airport-name resolution** (`resolve_iata` in `parsers/shared.py`): scored, accent-folded, word-boundary matching using the `type` / `scheduled_service` ranking columns; returns `''` rather than guessing
- **Ollama LLM fallback** (optional): set `OLLAMA_URL` + `OLLAMA_MODEL` in `.env`; used as last resort for incremental sync; `run.sh` auto-starts Ollama if binary present; optional `ollama` service in `docker-compose.yml`
- CLI eval tool: `uv run python -m backend.tools.eval_eml_files` — tests LLM against `.eml` files (pass file or glob)
- Corpus coverage tool: `uv run python -m backend.tools.corpus_report` — runs every tier (rule → GDS merge → timezone → validation, plus stays, rentals, boarding passes, cancellations) over `data/email_cache.json` and prints per-rule matched / produced / nothing, with the silent mails listed by subject. `test_corpus_report.py` drives it on in-memory fixtures
- Blocked sender domains: admin-managed list of domains silently skipped during sync (e.g. Airbnb, Booking.com)
- Manual sync trigger and configurable sync interval + email limit (admin)
- Full sync re-reads every mail in the lookback window (the processed-mail ledger is cleared); a parser update triggers one such rescan automatically on the next sync
- **Upload .eml files directly** from the trips list (`POST /api/sync/upload-eml`): parses uploaded `.eml` files through the same engine (rules → GDS e-ticket → LLM) and imports flights
- Inbound SMTP server (aiosmtpd, default port 2525) for email forwarding

### Flight enrichment
- Aircraft type lookup: AviationStack → OpenSky Network fallback; result cached

- **Stats collapses duplicate legs before counting anything** (`stats/service.py::_dedupe`, keyed on route + both timestamps). Nobody flies the same route at the same minute twice, so a second identical row is a parsing artefact — a SAS confirmation printing "SK4698 | Airbus A320neo" has been read as two legs, the second numbered `A320`. It doubled the distance and the CO2, and worse: the phantom sat **between the two halves of a connection** and broke the adjacency the 24h layover rule walks, so a 1h05 change of planes in Oslo counted as having visited Norway. Note this also collapses codeshares, which is correct — one aircraft, one flight.
- **Wrong countries in Stats are almost never a Stats bug.** A real report of "countries she never visited" came from two bad rows: the phantom above, and a Ryanair itinerary parsed to `YXU→FFA` (London **Ontario** → First Flight, North Carolina). The root cause was that the live instance's `airports.type` / `scheduled_service` were **NULL** — `backfill_rank_columns` had never completed there — so `resolve_iata` could not prefer Heathrow over London, Ontario. Check `SELECT COUNT(*) FROM airports WHERE type IS NULL` before suspecting the layover rule. `GET /api/settings/airports/count` now returns `ranked` alongside `count`, and Settings warns when they differ, because that degradation was otherwise a single startup log line nobody reads.
